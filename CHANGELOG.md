# Changelog

## Unreleased

- engine (ENG-3b): `claude --resume` / `--continue` picks its workflow sessions up by itself. The SessionStart hook (`source: "resume"`) runs the new `build/session-cli.js pickup`: every session stamped with the resumed conversation id that is suspended — or owned by a dead process (a crash past SessionEnd) — is handed to the new process with its whole active sub-tree (each file under `Storage.update`'s lock, via `takeOver` in the new `src/takeover.ts`, which `Engine.resume` now uses too) and every suspension in it is cleared; a session another live process runs is left alone — so is a descendant it runs unsuspended, and a session whose parent is active (it is the parent's to hand over, e.g. the child an explicit `resume` left suspended in another process). The hook prints `picked up: <session> @ <workflow @ state>` per root, its exec in flight, and the sub-agent sessions with the `SendMessage` that wakes each agent — the agent calls `status` on its own session (no `resume`). The first `status` / `transition` of a session whose foreground exec a previous server left running (`running_exec`, not this server's own: `_inFlight`) takes it over like `resume` (waits, takes the recorded result, or re-runs); a `transition` then answers with the routed state as an error (`isError`) and is NOT taken. Without a build or node the hook falls back to the ENG-3 listing for an explicit `resume`; `startup`, another account and `--fork-session` stay explicit (`suspended()` + `resume`). `source: "compact"` / `"clear"`: the hook appends this process's active sessions as a tree (id, workflow @ state, nested stack, agent, exec in flight) to its output, which lands in the new context. The startup reaper re-checks the dead owner under the lock, and re-reads a session before expiring it, so a hook handover between its read and its write is neither re-suspended nor abandoned. Deploy note: `npm run build` (the hook needs `build/session-cli.js`), then restart the Claude sessions

- engine (ENG-5b): an exception inside an exec's `close` / `error` handler (e.g. `_runResult` failing to read the result files) now ends the step with exit 1 and the error text instead of being lost or killing the server; `index.ts` also logs `unhandledRejection` / `uncaughtException` to stderr and stays alive (Node ≥15 exits on them by default)

- engine (ENG-5): an exec killed by its `timeout` whose process-group reap fails (`_reapGroup` rejects) now ends with exit 124 and the reap error in `error`; it was an unhandled rejection — under Node ≥15 that exits the MCP server — and the exec never settled. The other `ast-grep` hits were checked by tests and are safe: the per-session queue in `tools.ts` hands a failed task's rejection to its caller and runs the next task (its tail now settles on both paths via one `then(release, release)`); a failed detached-run record in `_exec` is caught where it is made; `wf-run`'s `run()` executor is synchronous, so a throwing `spawn` rejects and `wf-run` exits 1 with the reason. Those sites carry `// ast-grep-ignore: <rule> -- <why>`. `npm run check` now runs `npm run scan` (`ast-grep scan --error`, rules/ as errors, 0 findings; needs `ast-grep` on PATH)

- engine (ENG-3): a restart no longer loses the workflow. SessionEnd SUSPENDS this process's active sessions and their active descendants (`suspended_at`, stack/context/children kept, no ledger line — nothing ended) instead of abandoning them; the hook no longer ends any session, so `build/ledger-cli.js` is gone. The SessionStart hook writes `$STATE_DIR/claude-session-<pid>` = the conversation id; `start` stamps it on the session (`claude_session_id`), SessionEnd stamps the ending one; on `source: "resume"` (`claude --resume` / `--continue`, same id) the hook lists that conversation's suspended root sessions with their `resume` call, on `startup` it lists nothing. New tools: `resume({ session_id })` — re-owns the session and its active sub-tree for this process, clears the session's own suspension (each child waits for its agent's `resume`), returns its state and lists the suspended sub-agent sessions as agent → session → state with the `SendMessage` that wakes each; `suspended({ all? })` — suspended sessions of this project (git root), for an account switch; `link_agent({ session_id, agent_id })` — which agent drives a child session. `transition` / `context_set` / `modify` refuse a suspended session and name `resume`. Foreground execs now run detached through a wrapper that writes output to files and the exit code to a file (`$STATE_DIR/exec/`), so an exec running at exit is not killed; the session records it while it runs (`running_exec`), and `resume` of a session stopped in that state waits for it (abort kills it, its `timeout` counts from its start), takes its recorded result, or — neither survived, e.g. a reboot (boot time checked) — runs the step again; its pool lease already lives while its process group does. A `fanout:` state is re-run; a result that cannot be routed (no target, max transitions) drops the run's files and record; the run dir (`$STATE_DIR/exec/`) is 0700 and server start removes run files older than a day that no session references. Behaviour changes of the file-based exec: a foreground exec resolves when its shell exits (a background child it leaves no longer holds the step open); a command killed by a signal exits 128+signal (was 1); a timed-out run resolves only after its whole group is gone (SIGTERM, SIGKILL after 5 s); `max_output` counts bytes (was characters); the output files are not capped while the command runs (`yes` fills the disk until its `timeout`). `--fork-session` gets a new conversation id, so its SessionStart hint lists nothing — `suspended()` finds the sessions. Server start suspends the sessions of dead processes (a crash past SessionEnd; was: abandon) and abandons, with a ledger line, sessions suspended longer than `WF_SUSPENDED_TTL_DAYS` (default 7; history event `expire`). Plan resume from a new process now says `resume` first. Deploy note: `npm run build`, then restart every Claude session — sessions of a process still running the OLD hooks are abandoned at its exit as before; only processes started after the build suspend

- engine (ENG-2d): `extends: <workflow>` — a workflow file inherits another: the base's states plus its own laid over by name (a same-named state replaced whole, new ones added), `initial` / `max_transitions` / `description` from the heir when set; `extends` of its own name resolves from the tiers below the file (a project `coding` with `extends: coding` inherits the global/bundled one), another name from the top tier; chains, cycle / missing-base detection, validation on the merged result (a file that fails it falls back to the same name one tier down, as a schema failure always did); without `extends`, `initial` + `states` stay required (strict). Extension points with contract names in the bundled templates: `testing` gets `project_test` (the run half of the old `unit_tests`: `unit_tests` now writes and hands over via `run`; `project_test` routes `pass` → check_integration / `fail` → fix_unit as before), `project_build` (build before integration; a fix round rebuilds; `fix_integration` gets `max_visits: 5` → `failed`, since a failing build loops there without passing integration's budget) and `project_gate` (bundled: `exec true` → done, so no gate; every path to `done` passes it, `assess.skip_all` included); `bug-fix` gets `project_build` before `verify_visual`. Bundled defaults keep the old behaviour (agent-run prompt or no-op); a project heir overrides them with execs. `fanout: { count | items_command, threads_each, max_parallel? }` on an exec: N instances (`WF_SHARD=i/N` 1-based, or `WF_ITEM=<line>`), each with its own pool lease of `threads_each` threads (`WF_THREADS`), at most `max_parallel` in flight (default: what the budget runs side by side, so the pool queue does not fill with the whole fan-out); `items_command` lines lose a trailing `\r`; `timeout` per shard; exit 0 only if all are 0, else their common code (all timed out → 124) or 1; `{{stdout}}` = summary + failed tails; abort kills / withdraws / starts no more; history and ledger carry `shards` (per-shard exit, run, wait, threads); load error beside `background` / `resource` (so no `wait_timeout` / `locks` / step `priority` for shards — a known limitation). `on_timeout: <state>` on a foreground exec routes a run killed by its `timeout` (124) apart from `on_error` / `cases` (load error beside `cases: {"124": …}`). Deploy note: a server built before this rejects `extends` / `fanout` / `on_timeout` workflows (unknown key) and still has the old `testing` / `bug-fix` routes — `npm run build`, then restart every Claude session (templates are read at boot; running sessions keep their snapshot)

- engine (ENG-2b): session priority levels — `low` −100 / `normal` 0 / `high` 100 / `urgent` 200: `start({ priority })`, inherited by child sessions, default `normal`; a lease's priority = the level + the step's `resource.priority` (fine-tuning within the level). New tool `set_priority({ session_id, level })`: changes a session and its active descendants on the fly and re-ranks their WAITING pool entries at once (running leases untouched, no preemption); it runs outside the session's queue, changes each session through the new `Storage.update` (read-modify-write under the session file's lock, so a session that ended meanwhile stays ended), and the action chain keeps the level written during its exec; contended session-file locks now retry instead of failing. Every exec gets `WF_PRIORITY` (the sum) + `WF_PRIORITY_LEVEL`; `wf-run` without `--priority` queues at them (and passes `WF_PRIORITY` to its child). Flexible leases: `resource: { threads: { min, max: N|budget }, wait_full: SEC }` and `wf-run --threads A-B [--wait-full SEC]` — the max when it fits, else after `wait_full` (default 0) every thread that fits if ≥ min; `WF_THREADS` = granted; a waiting flexible head closes the threads behind it like any waiter (no overtaking); `threads: N` = `{ min: N, max: N }`. `wf-run --status` and the new `pool_status` tool print one line per lease/waiter: pid, held/wanted threads and locks, priority + level, since when, project (git root; a linked worktree → its main repo), session, step, label. History and `ledger.jsonl` of a leased exec record `threads_granted` and `step_key` = `<project>|<workflow>|<state>` beside `wait_ms`/`duration_ms` (raw data for a time model; nothing is modelled). Deploy note: a server or `wf-run` built before this knows neither levels nor the flexible form (a `{ min, max }` workflow fails its load, an old pass treats a flexible waiter as a fixed request for its max) — restart every Claude session after the build

- engine (ENG-2a): the leased command learns its share — an exec under `resource:` with threads and the child of `wf-run` get `WF_THREADS` = the threads granted (after `budget` and the clamp to the budget); a light exec, a lock-only lease and `--efficiency` get none (an inherited value is dropped). Documented recipe: pass it to `-j` / `--maxWorkers` / `HXCPP_COMPILE_THREADS` / `APQ_ORACLE_PARALLEL` — compilers and test runners otherwise take every core whatever the lease says. Named locks: `resource: { locks: [NAME, …] }` (`threads` now optional beside `locks`, at least one of the two — a schema error otherwise) and `wf-run --lock NAME` (repeatable; without `--threads` a lock-only lease) — machine-wide mutual exclusion by name in the same `pool.json`, granted atomically with the threads (all or nothing, nothing held while waiting → no deadlock); nothing overtakes a waiter on what it waits for (threads as before, a lock in queue order), and a waiter blocked by a held lock claims no threads, so a long-held dev-server lock does not stall the queue; a lock-only lease is never blocked by load; dead holders reaped, abort withdraws, `wait_timeout` → 75, `--status` lists held locks, `--efficiency` keeps its locks. templates: file-review `mechanical_pass` and lint-review `run` lease `{ threads: 4, priority: 1 }` behind a lease-free probe (`mechanical_probe` / `probe`, `hxq-lint-file.sh` with `LINT_PROBE=1`: exit 0 + SKIP lines when there is nothing to lint, 10 when there is) — a review of a non-Haxe file never queues; under a lease the script sets `APQ_ORACLE_PARALLEL` from `WF_THREADS` unless the caller set it. Deploy note: a server built before locks ignores them — restart every Claude session before relying on a lock; an exec lease also names its child's process group, so a server that dies mid-exec keeps its lease (and locks) until the group exits
- engine (ENG-1d): `status({ session_id, key })` returns one context value WHOLE (a string as is, anything else as pretty JSON; an unset key errors with the key list) — the plain status still cuts values to 200 chars and now names the call on a cut value; works on finished sessions, no ownership check (as status). A state's `on_exhausted: <state>` turns a move past its `max_visits` into a move into that state instead of an error — for agent transitions, action-state routes and skill-gate auto-transitions alike (chained routes followed, a cycle is an error, the history `detail` names the exhausted states, a rerouted action move shows the routed-to state's own prompt instead of the action's `success_prompt`/`error_prompt`; load error without `max_visits` or to an unknown state); without it nothing changes. `resource: { threads: budget }` and `wf-run --threads budget` lease the whole configured budget (any other string is a load / usage error). The contract that `{{stdout}}` / `{{stderr}}` / `{{exit_code}}` (the session's `last_action_result`) reach the routed-to state's own prompt, later prompt states and the next action's command/env is documented and pinned by a test
- engine (ENG-1b): machine-wide thread pool for heavy work. `wf-run [--threads N] [--priority P] [--wait-timeout SEC] [--label TEXT] [--efficiency] -- <cmd>` (`bin`, shim `scripts/wf-run`) and the exec field `resource: { threads, priority?, wait_timeout? }` take a lease from one pool dir per machine (`$WF_POOL_DIR`, default `~/.claude/workflow-pool`, independent of `CLAUDE_CONFIG_DIR`); admission under a file lock: `held + N <= budget` and, beside a live lease, `held + N + external <= budget` — external load never blocks an empty pool (`budget` default performance cores − 2, `external = max(0, load − held − load_threshold)`, `load_threshold` default 2; `load` = busy cpus over the cpu-tick window since the pool's previous pass, loadavg1 only as the fallback before a window exists), strict priority/arrival order without overtaking, `N > budget` waits for an empty pool, dead entries reaped every pass (a `wf-run` lease also lives while its child's process group does, so a SIGKILLed `wf-run` cannot push its child outside the budget); busy past the wait timeout = exit 75. `wf-run` runs the child in its own group, forwards SIGINT/SIGTERM/SIGHUP, exits with its code, `--status` lists leases and the queue, `--efficiency` (macOS) runs under `taskpolicy -b` outside the budget. Exec history and ledger record `wait_ms` (ledger `wait_ms_total`), `{{wait_ms}}` is a template var; an abort that lands as the lease is granted gives it back without running; `resource:` is strict and a load error on a background exec or a fetch. `killProcessGroup` moved to `src/process.ts`
- engine (ENG-1a): `start` takes an optional `cwd` (absolute, existing dir → `context.cwd`; execs without their own `cwd:` run there, a relative one resolves against it) — a sub-agent's execs run in its worktree, not the server's tree. Execs get `WF_SESSION_ID` / `WF_PARENT_SESSION_ID` (empty at the root) / `WF_ROOT_SESSION_ID`, prompts `{{session_id}}` / `{{parent_session_id}}`. A root ending on a `fail` terminal is now `outcome: "failed"` (was recorded as completed); `status` / `sessions` / dashboard show it. `status` lists the session context (values cut to 200 chars, keys past 40 folded) so a parent can read a child's results. `abort` and a parent's abort cascade kill each background exec's process group (was: the bare pid, leaving `sh -c`'s children) and in-flight foreground execs. Unknown YAML keys fail the load, naming file, state, key and nearest known key (all bundled + user + anyparse workflows load clean). Each exec's history entry records `exit_code` + `duration_ms`; every session end (complete / fail / abort / cascade / hook abandon via `build/ledger-cli.js`) appends one line to `$STATE_DIR/ledger.jsonl`. `workflow-start.sh` deletes `context-epoch-<pid>` markers of dead pids

## 0.1.11

- templates: testing — the fix-loop states (`fix_unit` / `fix_integration` / `fix_user_issue`) gain delegation discipline: a small, already-diagnosed fix is edited INLINE, not handed to a background `SendMessage`-resume and idle-waited on.
