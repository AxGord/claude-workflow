# hxq mutation ops — full contracts, safety boundaries, caveats

## Refactoring ops (`hxq <op>` — source MUTATION, not query)

Distinct from the read-only query subcommands above: these REWRITE source. All are **scope-correct** (reuse the `refs`/`Scope` resolver, not by-name text replace), **format-preserving** (span-splice; everything else byte-verbatim), and **re-parse-validated** (a rewrite that doesn't parse is rejected, never written). **Every `<l>:<c>` slot in the tables below ALSO accepts `--select '<sel>'` / `--match '<pattern>'` [+ `--nth <k>`] and the bare `<line>` form — see “Addressing (v2)” above; prefer those, the positional form is the legacy fallback** (exceptions: `extract-method` ranges and `set-comment` stay positional; `extract-var` takes `--match` but not `--select`). Default prints the rewrite (or a summary) to stdout; `--write` applies in place. **Coordinate convention = 1-based `<line>:<col>`** — identical to what `hxq refs`, `ast --at`, `source`, and your editor print (no `col-1`/`col+1` inversion — a col copied from any of them lands correctly).

Build-after (`haxe test-js.hxml`) is still prudent for any field rename in a macro class, but the historical 8338-`Unknown identifier` over-rename is fixed. CAPTURE GUARD: the rewrite is re-resolved and the binding's occurrence set must be unchanged, so a new name a param/local already holds in an overlapping scope is REFUSED (`x = x` self-assignment compiles — no typecheck would catch it); `--qualify-shadowed` emits `this.x = x` instead, but only for a capture by a PARAMETER in a non-static function. REMAINING GAP: a bare `$name` macro-reification SPLICE (a macro-time local's value injected into a `macro` expression as `$name` — distinct from a `${…}`/`$v{…}` interpolation, which IS indexed, and distinct from the `$name` STRING-interpolation blind spot the resolver already refuses) is NOT indexed as a reference, so `rename` neither renames it nor refuses — it rewrites the decl and every ordinary read/write but silently leaves each `$name` splice bound to the OLD name. **Structural insert / replace ops — WRITER-EMIT:** a SECOND mutation sub-family, distinct from the scope-correct span-splice refactoring ops above. These introduce NEW code, so they are **writer-emitted, NOT spliced as-is**: the raw new text is placed at an AST-resolved position, then the WHOLE file is re-emitted through `writeRoundTrip` (the trivia/comment-preserving pipeline), which formats the inserted code by the grammar's own rules AND re-parse-validates in one step (unparseable → `Err`). Because a whole-file rewrite would also reflow unrelated hand-wrapping, there is a **canonical gate**: unless `--reformat`, the file must already satisfy `writeRoundTrip(f) == f` (else `Err` "not canonical"); `--reformat` opts into canonicalising the whole file (the gofmt workflow). **anyparse src/ is writer-canonical**, so the gate passes on src files; the project `hxformat.json` is auto-DISCOVERED (walk up from the edited file via `Cli.discoverFormatConfig`) and threaded into the writer, so the result matches the project style. Shared finalize `RefactorSupport.canonicalize(source, edits, reformat, plugin, ?optsJson)` + unified `RefactorSupport.EditResult { Ok(text); Err(message); }`; each op is a thin `final class` (`src/anyparse/query/{ReplaceNode,AddMember,AddImport,AddElement,ExtractMethod}.hx`). Requires a grammar with a writer; result is FULLY canonical (whole-file gofmt), NOT a minimal diff of just the change. **CODE INPUT:** the `<code>`/`<memberText>`/`<newSource>` positional arg of `add-member`/`add-element`/`replace-node` accepts `--from-file <path>` OR the literal `-` (read from stdin, like `probe -`) — the QUOTE-SAFE path for code containing `$` (Haxe interp) or `'`/`"` that the shell mangles as an arg. **USE THIS to drive the ops from bash** instead of the heredoc-into-var trick. **PREFER stdin via a quoted heredoc** — `hxq add-member f --type T - <<'EOF'\n<code>\nEOF` — it is quote-safe (the `'EOF'` quotes suppress `$`/backtick/`'`/`"` expansion, so Haxe interpolation reaches stdin verbatim) AND a single bash call: no Write-temp-file + `--from-file` + `rm` round-trip (that 3-step path is the costlier default I kept reaching for — don't). `--from-file <path>` is for when the code ALREADY exists as a file or is reused across several ops. `printf '%s' "$code" >/tmp/m.hx` then `--from-file` works too but only earns its keep on reuse. Giving the code by more than one route → `Err`. Shared resolver `Cli.resolveCodeArg`.

**Ops note — `add-element` / `remove-element` TOLERATE a cursor within a node's first token.** The `<l>:<c>` does not have to be the EXACT `span.from`; a column anywhere inside the node's opening token (one past the `{`, or inside a name) resolves the same node — so **the column can be taken straight from `ast --at`** (which forgivingly returns the innermost node *containing* the cursor, not necessarily one starting at it). No need to derive the exact first-token column by hand. `--append` resolves the DEEPEST container whose first token holds the cursor (inclusive bound → an inner `[[` resolves the inner array); `--after` / `--before` and `remove-element` resolve the outermost ELEMENT whose first token holds the cursor, EXCLUSIVE of the delimiter boundary (so a container's `[` / `{` does not swallow the first element that starts right after it). Backed by the shared `RefactorSupport.elementAtFrom`; the internal `nodeAtFrom` stays EXACT for the binding-span callers (`CallSites` / `ExtractMethod` / `Inline`).

`--after`/`--before` anchored on a bare string-literal element inserts correctly between elements; no whole-array replace needed.

**Ops caveat — `remove-member` WITHOUT `--with-doc` orphans the removed member's OWN doc.** The doc block is leading trivia, not part of the member node, so the op deletes the member and leaves the `/** */` behind — where it re-attaches to whatever declaration follows, which then carries TWO doc blocks, the first one describing something that no longer exists. **Ops caveat — `remove-member`/`remove-element` can leave a DOUBLE blank line at the deletion boundary (the delete-side twin of the `add-member` note above).** When the removed member/element sat between a blank line above AND a blank line below, the op swallows only the member's own physical line, so the flanking blanks collapse into two consecutive blanks — pure trivia, so it survives the canonical gate and `hxq fmt --list`/`-l` reports nothing. **Ops caveat — `add-member` can silently violate `member-order`.** `member-order` ranks methods by static-ness as well as visibility: instance methods sort BEFORE static ones (`PublicMethod` < `PrivateMethod` < `StaticPublicMethod` < `StaticPrivateMethod`). `add-member` is APPEND-ONLY (lands last in the type body). **Writer-emit working discipline — prefer ops over Edit, but know the writer's limits:**
- **Edit is what makes files non-canonical.** Hand-written code drifts from the writer's form (e.g. a `['a','b',…]` array on one line that exceeds 140 cols — the writer wraps it one-element-per-line). Then the next writer-emit op REFUSES (canonical gate). The writer-emit ops are IDEMPOTENT — `op(canonical) == canonical` — so a file mutated ONLY by ops stays at the canonical fixed-point forever and every op keeps working. **Default to the ops; surgical mid-logic rewrites are `hxq patch`'s job now** (old `====` new via heredoc — no whole-declaration resend); Edit remains only for what no op covers (rare trivia-only shapes) and must be written in canonical shape, or `--reformat` after.
- **`--reformat` is the FIX for drift, not a hazard.** On a file that is SUPPOSED to be canonical (the project's own `src/`), the "extra" lines `--reformat` touches are correcting your own Edit-drift — desirable, not noise. Don't fear it.
- **MEASURE canonical-ness, never guess from file SIZE.** Drift ∝ accumulated non-canonical Edits, NOT line count — an 8000-line file mutated only by ops gives a clean one-member diff; a 100-line file you Edited gives more. One command tells you: run the gate IN-TREE — `hxq add-member <file> --type T 'x' >/dev/null 2>&1; echo $?` (exit 0 = canonical, 1 = not), or `… --reformat --write` then `git diff --stat`. (Declining an op because a file is "big" is the false-proxy trap.)
- **The gate reads `hxformat.json` via `discoverFormatConfig` from the FILE'S directory upward.** So testing canonical-ness on a `/tmp` COPY gives a FALSE refuse (no `hxformat.json` there → default opts, e.g. `:Array` vs the project's `: Array`). Always gate-check the file IN ITS PROJECT TREE.
- **`ast --writer-output` uses DEFAULT opts, NOT the project config** — it is the wrong tool to canonicalize to project style. There is no standalone `format` command; canonicalize content-neutrally with `hxq replace-node <file> --select PackageDecl '<the exact package line>' --reformat --write` (replace a decl with itself + whole-file re-emit through the config-aware path).
- **Canonicalization is SAFE for the catch case** — the `} catch  (` double-space bug is FIXED (root was `HaxeFormatConfigLoader.applyConditionParens` deriving BOTH the kw→`(` gap AND the inner `( ` pad from one `openingPolicy` under `conditionParens.openingPolicy:"before"` — config-specific, NOT the trivia non-idempotence first guessed). Re-emitting a project-tree file does not bake `catch  (`. **Still eyeball the `git diff` of any canonicalization before committing** — if it introduces ARTIFACTS (not just clean wrapping/spacing) there may be ANOTHER writer non-idempotence; then leave the file non-canonical and use `--reformat` per-op. `--from-file`/`-` closes the QUOTING gap but NOT the canonical-gate — ops still need the file canonical (or `--reformat`).

**`final`-decl handling:** `final` is the one modifier that WRAPS a decl, so a `final` declaration projects to a DIFFERENT kind than its plain form. **Decl-kind cheat-sheet:** `final class X`→`FinalDecl(ClassForm X)` (the NAME is on the inner `ClassForm`, the `final ` keyword is in the outer `FinalDecl` span); `final function d()`→`FinalModifiedMember`; plain `class`→`ClassDecl`; plain method→`FnMember`; `final` FIELD (`final x:Int`)→`FinalMember`; every OTHER modifier (`public`/`private`/`static`/`override`/`extern`)→a SEPARATE preceding sibling node before a plain decl. **All refactoring ops HANDLE final decls:** TYPE ops (rename `--scope` / move / SymbolIndex) handle `final class` via shared final-aware `RefactorSupport.typeDeclOf`/`resolveTypeDeclAtCursor`; FN ops (rename / change-sig / add-param / extract-var, + remove-param) handle `final function` — via the QUERY-PROJECTION layer (`HaxeQueryPlugin.extractName` surfaces the method name off the inner `HxFinalModifierMember.fn` onto `FinalModifiedMember`, which then joins `DECL_HOST_KINDS`/`scopeKinds`); the shared `RefactorSupport.FN_DECL_KINDS` (`FnMember`/`FinalModifiedMember`/`LocalFnStmt`) backs all fn-ops. Methods INSIDE a `final class` are normal `FnMember`. **`hxq ast --select` is final-aware too:** `--select ClassDecl` matches a `final class`'s `ClassForm` and `--select FnMember` matches a `final function`'s `FinalModifiedMember` (chains too — `--select 'ClassDecl > FnMember'` reaches a final method inside a final class), via `GrammarPlugin.selectKindEquivalence` folding `ClassDecl≡ClassForm` / `FnMember≡FinalModifiedMember`. This `--select` fold is SEPARATE from the search-only kind-equivalence and does NOT fold a `final` FIELD (`FinalMember` stays its own kind). So you don't need to remember the wrapper kinds for `--select` on classes/methods — but a `final` field is still `--select FinalMember`. The `--select` fold covers `final` shapes ONLY — `abstract class` projects as `AbstractClassDecl`, which `--select 'ClassDecl:X'` does NOT match; address an abstract class as `--select 'AbstractClassDecl:X'` (same for `source`/`patch`/`replace-node` targets).

**Modifier flips = `hxq set-modifier`; `replace-node`'s span always covers the WHOLE decl incl. leading modifiers.** A `replace-node` target (any address mode) resolves to the co-starting wrapper spanning the ENTIRE declaration — so `<newSource>` must be the complete decl with modifiers verbatim (`private static function walk(…)`, not bare `function walk(…)`). The silent-corruption trap (bare `'public'` as newSource would eat the declaration body) is GUARDED IN-TOOL: a newSource consisting of a single modifier keyword is refused with an Err pointing at `set-modifier`.

**`replace-node --at <l:c> --kind <Kind>` can resolve a CO-STARTING node of `<Kind>` that ENCLOSES the one you mean — a silent-corruption hazard.** Editing the inner `return X;` of `return arr.filter(v -> { … return X; })` via `--at <innerReturn> --kind ReturnStmt` grabbed the OUTER `return arr.filter(…)` ReturnStmt (both contain the cursor, both are `ReturnStmt`) → the new `return X;` replaced the WHOLE outer return, the filter/lambda body vanished, and the file still PARSED (caught only on the next build / `source` read). **FIX: don't use `--at --kind` for nested statements at all — `--match '<the exact statement>' --kind <Kind>` (lift semantics, exactly-one discipline) or `--select 'FnMember:<fn>'` (replace the whole function) have no co-starting ambiguity.** `--at <l> --kind <K>` remains only for operator nodes a pattern can't spell easily; if you must use it, probe `ast --at` first.

**FIXED (2026-10-17, anyparse N10/N12) — `move-member` carries `import`s AND the `using`s the moved code calls.** Carried statements land canonically: imports sorted, a blank line, then the `using`s in source order, then guarded blocks; a destination with no imports gets an import seat of its own (`importLessSeat`). A `using` whose extension methods the moved code never calls is NOT carried (same test as `unused-import`). Sub-type imports of the source module (`import <module>.<Sub>;`) are carried too (a private sub-type is still a refusal). Other N10/N12 behaviour worth knowing before a split:
- mutable fields that ONLY the moved group references travel with it automatically (fixed point; refused when anything else reads them, the refusal names the readers);
- receiver-qualified callers (`_g.x()`) are routed through the holding field (`_g.library.x()`) when the receiver is PROVEN the source class or a subtype; a receiver proven an unrelated class/interface is left alone; anything else (unknown, Dynamic, abstract, typedef/structure, `super`, `?.`) is a refusal;
- `--keep-bare` keeps bare calls in the source bare through one `import Dest.*;` (refused when the wildcard could rebind any name);
- private access needed by 2+ moved members gets ONE type-level `@:access` on the destination;
- `override`s, interface/abstract implementations and members a subclass overrides are refused;
- `--scaffold` wires the via field right after the last constructor statement that writes a field from the destination's arguments (and after `super()`), so `@:nullSafety(Strict)` constructors still compile.

**Ops caveat — `move-member` can leave the DESTINATION file non-canonical, so the NEXT writer-emit op on it refuses (not only when a `using` needs re-adding, per the note above).** Cause: the moved bodies' sibling calls get requalified to `Src.member`, which lengthens those lines — a call that fit the width before now doesn't, and the writer would re-wrap it. `move-member` is a verbatim splice with NO canonical gate, so it writes happily regardless; the next `patch`/`add-member`/`add-import`/`set-doc` on that file then errors `apq patch: file is not in canonical form — format it first`. Rule: run `hxq fmt <dest> --write` immediately after EVERY `move-member`, before any writer-emit op on it. (`--keep-bare`, since 2026-10-17, avoids the requalification where the source called the members bare.)

**Ops caveat — a class-level `@:meta` is a SIBLING of the type node, so `patch --select 'ClassDecl:X'` can't reach it.** The fragment `@:nullSafety(Strict)\nfinal class X {` errors "the old fragment does not occur in the resolved ClassForm node" — but `patch --at <metaLine>:1` DOES resolve it: the cursor lands on the `MetaCall` node (`hxq ast --at <line>:1 --depth 1` prints `(MetaCall @:nullSafety …)`), so patching that node's own text with itself plus a new line above adds a `@:access(...)`/any other class-level metadata without retyping the declaration. (Since `e8ec6cc1` prefer `hxq add-meta` — the `patch --at` recipe still works but needs an existing metadata node; whole-class `replace-node --select 'ClassDecl:…'` works since 2026-10-17 but retypes the whole type.)

**Ops caveat — `move-member` auto-PROMOTES every moved non-public member that still has a caller outside the destination.** That's a visibility (API) change the advisory reports but nothing gates — and it has a second-order cost: `doc-coverage` fires on "a public API type or member without a doc comment", so a batch of previously-private helpers arrives as a pile of new doc-coverage findings. When the project idiom is `@:access` rather than promotion, restore it in two steps: `@:access(<pkg>.<Dest>)` on the SOURCE type (`hxq add-meta <src> --select 'ClassDecl:<Src>' '@:access(<pkg>.<Dest>)' --write` — works whether or not the type already carries metadata), then `hxq set-modifier <dest> --select 'FnMember:<name>' private --write` per moved member (`FinalMember:<NAME>` for moved constants). Do the `@:access` first and run the intermediate ops with `HXQ_AUTO_REBUILD=0`, since each single-member state in between doesn't compile.

**FIXED (2026-08-13) — every import insert goes through ONE seat, `ImportOrder.insertionFor`.** `add-import`, the `explicit-local-type` / `shorten-type-ref` / `prefer-typed-throw` materialisers (`TypeRefPrinter`), `move` / `move-member` (`MoveSymbol.importAnchor`) and the `import-order` RULE all ask it, so they cannot disagree about where a file's header is. It resolves the `#if … #end` region guarding a module's WHOLE body as the header (`headerRootOf`), so a fresh import takes its sorted slot INSIDE the guard and a guard with no imports of its own anchors at the `#if` line end. A root-package `package;` anchors correctly too — it projects as `PackageEmpty`, a different node kind from `PackageDecl`, and every ladder that knew only the latter fell through to the file start and emitted `import` ABOVE `package`, which does not compile. Before the unification the ladder existed in three hand-rolled copies that had drifted apart (only one preferred a plain import over a `using`, only one knew the root package, none knew the guard).

**FIXED (2026-09-02, `e8ec6cc1`) — `hxq add-meta <file> (--select|--match|--at) '<@:meta>' [--nth] [--kind] [--reformat] [--write]` adds module-level AND member-level metadata to an existing declaration.** It lands BELOW the doc comment, at the END of the existing metadata run, ABOVE the modifiers (`final`/`private`/`static`…); a duplicate metadata NAME is refused; a `#if`-guarded declaration keeps the entry INSIDE the guard; it goes through `canonicalize` and honours `hxformat.json`. Add only — `remove-element --select 'MetaCall:@:name'` already removes metadata at both levels. Dogfooded: `@:nullSafety(Strict)` on `HxComprehension` in one added line; 45/45 module-level + 39/39 member-level census sites produce exactly one added line. The old caveat's MECHANISM was also wrong: `add-element --before --select 'ClassDecl:X' '@:meta'` succeeds at rc 0 on a plain `class`/`interface`/`enum`/`typedef` (it just lands ABOVE the doc, an ordering nothing in the repo uses — see the `add-element` note); only `final class` failed, on the `FinalDecl` wrapper.

**FIXED (2026-08-17) — `hxq move` no longer drags the NEXT declaration's doc, and a module-level `private` type moves.** One root cause behind both: `MoveSymbol` cut the RAW parse span. A `@:trailOpt(';')` decl written WITHOUT the `;` ends its span at the next declaration — past the blank line and past that declaration's `/** … */`, which the parser re-stashes as the neighbour's leading trivia — so the neighbour's doc travelled to the destination as an orphan while the neighbour was left bare (silent: build, suite and canonical gate all stayed green). And a modifier projects as a SEPARATE sibling BEFORE the decl, so `private typedef X` failed the "line-up-to the decl must be blank" guard and refused with `the type "X" shares a source line with other code`, naming a layout problem that was not there. The cut is now the modifier-folded, trailing-trimmed span (`declGroupSpan` + `trailingTrimmedSpan` — the same 816bb666 seat `replace-node` / `remove-element` / `patch` / `source` use), so the neighbour keeps its doc byte-for-byte, `private` travels to the destination with the type, and the blank separation is still collapsed at the source. Red tests: `MoveSymbolSliceTest.testMoveKeepsNextDeclDoc`, `testMovePrivateModuleType`. **One refusal came WITH the private unlock:** moving a module-`private` type that the source STILL references is refused (`the type "X" is module-private and <file> still references it after the move`), because Haxe cannot import a module-private type from another module and the op would otherwise write an `import` that does not compile. Make it public, or move its remaining uses too. A private type the source no longer references moves fine.

**Ops caveat — `hxq move` repoints only importers whose import path names the moved type EXACTLY; a SECONDARY (sub-module) type reached any other way is left dangling.** Moving `RefactorSupport.TypeDeclMatch` across a real tree repointed all 20 files carrying `import anyparse.query.RefactorSupport.TypeDeclMatch` and missed two other spellings that reach the same type: a MODULE import (`import anyparse.query.RefactorSupport;` — importing a module exposes its secondary types too) and a qualified type-position reference written inline with no import at all (`final m: RefactorSupport.TypeDeclMatch = …`). The op reports `wrote 22 file(s)` and exits 0; the misses surface at the NEXT build as `Type not found : TypeDeclMatch` (and, cascading, `Type not found : RefactorSupport`) — loud, never silent, but only if you build. Fix each site by hand: `hxq add-import <file> <new.module.Path.Type>` for the module-import form, `hxq patch` for the qualified reference.

**Ops caveat — `hxq move` leaves the DESTINATION non-canonical, same as `move-member`.** The decl is appended carrying its own line terminator and the destination's original EOF newlines are re-appended after it, so the file ends `}\n\n`; a first-ever import inserted into a file that had none also lands with no blank line after `package`. `move` is a verbatim splice with NO canonical gate, so it writes happily and the next writer-emit op on that file refuses with `file is not in canonical form`. Run `hxq fmt <dest> --write` after every `move`.

**Ops caveat — no op addresses a TRAILING orphan comment at EOF; build a throwaway decl under it and delete both.** A comment with no declaration after it belongs to no node, so every address mode misses it: the last decl's `patch --select` region stops at that decl's own closing brace, `remove-element` needs an element, and `set-comment` can only replace a comment with another comment. Working three-step recipe: (1) `add-element --after --select '<LastDecl>'` with a throwaway decl — at MODULE level the insert overshoots the trailing doc and lands BELOW it, which is exactly the documented `--after` overshoot trap, here working for you; (2) `set-doc --select '<Kind>:<throwaway>'` with any placeholder — it collapses the WHOLE doc run above the target into the one block you pass, absorbing the orphan; (3) `remove-element --select '<Kind>:<throwaway>' --with-doc`, which takes the placeholder with it. Then `fmt --list` to confirm.

**Ops caveat — the `--scope` path-form false ambiguity applies to `hxq move`, not just `rename --scope`.** `hxq move src/pkg/F.hx <l>:<c> src/pkg/G.hx --scope /abs/root/src` refuses with `type "X" is declared in 2 files under scope — ambiguous` for a type declared exactly once, because the cursor file's relative spelling and the scope walk's absolute one count as two files. Spell the cursor path and the `--scope` the SAME way (relative+relative or absolute+absolute); a `declares`-confirmed-unique type reporting "declared in 2 files" is a path-form symptom, never a real duplicate.

## JSON files — the same ops, never python / sed (anyparse N47, 2026-10-19)

A `.json` path selects the `json` grammar plugin whatever `--lang` says (the shim's `--lang haxe` included), so
`add-element` (`--after` / `--before` / `--append` / `--sorted`), `remove-element`, `replace-node` and the readers `ast`
/ `source --select` work on JSON exactly as on Haxe. **Edit `test/testkit/mutation-arms.json`, an `apqlint.json`, an
`hxformat.json` with these ops — not with python, `jq`, `sed` or by hand.**

Vocabulary (the JSON grammar's ctor names; `hxq ast f.json` prints the tree):

| Node | Name | Address |
|---|---|---|
| `JObject` | — | `Member:<key> > JObject` |
| `Member` (one `"key": value` entry; span = key's quote .. value's end) | its decoded key | `Member:rules >> Member:thread-safety >> Member:registers` |
| `JArray` | — | `Member:registers > JArray` (the container `--append` / `--sorted` address) |
| `JString` | its decoded value | `Member:spawns > JArray > JString:api.APIRequest2.success` |
| `JNumber` / `JBool` / `JNull` | — | by `--nth`, or `--match` |

An array element is picked by VALUE (`JString:<v>`), by ORDINAL (`--select 'Member:arms > JArray > JObject' --nth 12`),
or by PATTERN: `--match` takes a JSON value whose `"$x"` / `"$_"` strings are metavariables — an object pattern must
list every member in order: `--match '{"name": "M-X", "type": "$_", "method": "$_", "force": "$_", "note": "$_"}'`.
A key containing `>` cannot be spelled in `--select` (the selector splits on it) — use `--match` or a position.

Recipes:
```sh
# append an arm (DeclaredArms order = JSON order, so --append, never --sorted)
hxq add-element test/testkit/mutation-arms.json --append --select 'Member:arms > JArray' - --write <<'EOF2'
{"name": "M-X", "type": "anyparse.query.Foo", "method": "bar", "force": "null", "note": "…"}
EOF2
# re-aim an arm: replace the whole object, addressed by pattern
hxq replace-node test/testkit/mutation-arms.json --match '{"name": "M-X", "type": "$_", "method": "$_", "force": "$_", "note": "$_"}' - --write <<'EOF2'
{"name": "M-X", "type": "anyparse.query.Foo", "method": "baz", "force": "null", "note": "…"}
EOF2
# move entries between two lists of a config
hxq add-element apqlint.json --append --select 'Member:registers > JArray' '"a.B.c", "a.B.d"' --write
hxq remove-element apqlint.json --select 'Member:spawns > JArray > JString:a.B.c' --write
# a new member next to a sibling, a value replaced
hxq add-element apqlint.json --after --select 'Member:closedWorld' '"throwers": []' --write
hxq replace-node apqlint.json --select 'Member:closedWorld > JBool' 'false' --write
```

The writer is FORMAT-PRESERVING: a parseable JSON file is always "canonical" (no `--reformat` needed), an edit changes
its own lines only, and what it adds is laid out like its siblings — one entry per line or inline as the container is,
the document's indent unit (tab or N spaces) and line end, the siblings' `:` spacing; a new object / array copies its
nearest same-kind sibling's shape, else its container's. Pass the element text compact; the layout is the writer's.
`remove-element` on the last entry also takes the `,` before it. Not covered (edit by hand, report the gap): `patch`,
`move-elements`, `--sorted` over objects by key, comments (JSON has none).
