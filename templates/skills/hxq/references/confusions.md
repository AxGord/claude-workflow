# hxq — Common confusions (full text)

Moved verbatim from SKILL.md; the index there lists each lead.

- **`probe`/`ast --depth N` SILENTLY TRUNCATES below N — never conclude a node LACKS a child from a depth-limited dump.** A `--depth 5` probe of `abstract A(Int){ function f() return this.x; }` printed `(FieldAccess x)` with no receiver, so I wrongly concluded abstract `this.x` carries no `IdentExpr this` child (and built a check around that); at full depth it is `(FieldAccess x (IdentExpr this))` — the child was just past the depth cap. When verifying a node's CHILD structure (does X have child Y?), use depth deep enough to reach the leaf, or `--select` the node and read it unbounded. A unit test caught the false invariant; a deeper probe would have caught it first.
- **`search --kind K` finds a node of that kind ANYWHERE, including nested inside a member — the hit line cannot tell you which.** Asking "which MEMBERS have an expression body" with `search '$x' <dir> --kind ExprBody` returns the local functions too: a `function helper() return …;` declared inside a block body IS an `ExprBody`, and its `file:line:col` looks exactly like a member's. Acting on such a hit means building a fixture for a shape you never found. The member-level question is a STRUCTURAL one and `ast` answers it: `ast <f> --select 'ClassDecl:<T>' --depth 3` prints each member with its own body node as a direct child (`(FnMember f … (BlockBody …))` / `(ExprBody …)` / `(NoBody …)`), so "whose OWN body is X" is read off the nesting rather than guessed from a position.
- **0 hits on `search`** — almost always a kind mismatch. Re-run with `--explain` to see parsed pattern + input-kind histogram. If the pattern's root kind isn't in the histogram, the search never hits — read actual node shape via `hxq ast` and rewrite.
- **`search` pattern BOOL LITERALS match by KIND, not VALUE** — `false == true` matches `true == true` (the operator `==` vs `!=` IS discriminated; the literal's text is not). A literal-literal search over-matches by value — confirm each hit with `hxq source --range`, or use `lit` for exact text.
- **A string literal's CONTENT lives in a different slot depending on the QUOTE, and neither spelling is decoded.** In the Haxe grammar `'x'` projects as a `SingleStringExpr` with **no name of its own** and one child per segment (`Literal` text runs, `Ident` for `$name`, `Block` for `${…}`); `"x"` projects as ONE `DoubleStringExpr` whose own `name` is the raw source slice **with** its quote marks. Both terminals are `@:rawString`, so `'a\tb'` is the four-character `Literal a\tb`, not a tab — `HxStringEscape` is what decodes. Three consequences: the DEFAULT `lit` kind set is the grammar's whole string-content vocabulary (`RefShape.stringInterpTextKind` + `stringLiteralKinds` minus the interpolating one) with the declared quotes stripped before the compare, so both spellings answer one query and `--exact` reaches either — before S188 the default named `Literal` alone and a scope holding the needle in BOTH spellings printed half its hits with no note at all, since the 0-hit auto-widen never fired; an explicit `--kind Literal` still narrows but now prints which spelling it dropped; reading `node.name` on a `SingleStringExpr` always yields null; and a walk listing SYMBOLS must drop both by kind, which is what `RefShape.stringInterpTextKind` + `stringLiteralKinds` are for. The asymmetry is a grammar contract, not a bug — a form that interpolates has to expose its segments, a raw terminal has none to expose.
- **"Find string `'foo.bar'`"** — that's `lit`, not `search`. Use `hxq lit 'foo.bar' <dir>`.
- **"Find annotation `@:trailOpt`"** — `hxq lit '@:trailOpt' src/ --kind Literal,Meta`.
- **`search 'function foo'` returns no decls** — `search` is expressions/statements (call sites), not declarations. Use `refs foo --decls` or `ast --select 'FnMember:foo'`.
- **TODO/comment text** — `hxq lit 'TODO' src/ --include-comments`. Replaces `grep + # HXQ_OK:prose`.
- **`refs`/`uses`/`blast`/`mentions` all return 0 but you know the name appears** — case-pattern usage. Try `cases Foo <dir>`.
- **Want `| head -N`** — every walker has `--limit N`; walkers also auto-cap at 500 hits without `--limit`. ⚠️ **`--limit 0` returns ZERO hits (a hard cap of 0), NOT "unlimited"** — verified on `lit`/`refs`. The truncation is no longer SILENT on the seven walkers that share `CliWalk.capAndReport` (`lit` / `refs` / `uses` / `meta` / `search` / `mentions` / `cases`): each prints ONE stderr line naming the cap, the files reached of the total and the last file — `apq lit: stopped at --limit 3 after 2 of 62 files (last: src/anyparse/format/wrap/WrapList.hx) — pass a larger --limit for a census`, and at zero `apq lit: stopped at --limit 0 after 0 of 62 files — pass a larger --limit for a census`. Exit code and stdout are unchanged, so a script that parses stdout is unaffected. **`blast` does NOT share that seam and still truncates silently.** To exceed the 500 default cap pass a large explicit `--limit N` (e.g. `--limit 9999`); to get ≤500 just omit `--limit`. Hits go to STDOUT (progress `scanned N/M…` goes to stderr (only when stderr is a TERMINAL since S166 — a pipe gets none; `HXQ_PROGRESS=1` forces it back on)) — capture stdout, not `2>/dev/null`-suppress it, when counting.
- **Sweeping an op over EVERY declaration of a kind** (a census: how often does this op fire, how often does it refuse and why) — you do not need names or positions. A bare `--select '<Kind>'` is the enumeration: `--nth 9999` fails with `--select "<Kind>" matched N node(s)` (that N is the count), and `--nth 1…N` then addresses each one in document order. Drive it over a file list with the op in `--write` mode on a COPY, and classify by the op's own stderr. The bare `--select '<Kind>'` ambiguity listing prints only the first 5 candidates, so it is not a substitute for iterating `--nth`.
- **Script-checking "is X gone?"** — pass `--exit-on-empty` (alias `--require-match`) to a find-walker (refs/uses/meta/lit/cases/blast/mentions/search), to `reach` (no path found), or to `callers`/`callees` (no edge line rendered — their stdout is NEVER blank, the root label always prints, so the exit code is the only machine-readable emptiness signal they have): 0 hits → non-zero exit instead of the default 0. Without the flag a walk always exits 0, so a bare `hxq refs X …; echo $?` can't distinguish found-vs-gone. `clusters` does not honour it and should not — its report is never empty, and it prints its own per-type resolved/unresolved coverage on stdout.
- **Output flood** (e.g. `lit '/*' src/ --any-kind`) — auto-truncated per-hit content (multi-line block-comments → first line + ` … +N lines`); auto-cap at 500 hits with stderr nudge naming the cap and the last file reached. Both opt-out via a large `--limit N` (NOT `--limit 0`, which returns nothing — see the `--limit 0` warning above).
- **`#if`…`#end` interiors ARE parsed and visible to walkers/lint — a 0-hit `refs` still means unused.** A conditional-compilation region is a single `Conditional` node whose children are every branch's statements flattened as siblings (no per-branch grouping) — `refs`/`uses`/`mentions`/`lit` and node-local rules (`unused-private`, `unused-local`, `collapsible-if`, `prefer-null-coalescing`) all see inside it fine. The real blind spot: STATEMENT-LIST rules only visit direct children of `ControlFlowSupport.blockKinds()` (`BlockBody`/`BlockStmt`/`BlockExpr` for Haxe) — `Conditional` is deliberately excluded, else `dead-code` would call branches 2..N unreachable after branch 1's `return`. So `redundant-else-after-return`/`prefer-ternary-return`/`join-return`/`dead-code`/`empty-block` stay silent on a statement that's a direct child of a `Conditional` — fix those by hand via `hxq patch`; there's no report to point at.
- **"What runs under flag X" is `hxq cond X <scope>`, not `lit --include-directives` plus guesswork.** `lit --include-directives` gives a directive's TEXT and a `line:col` and says nothing about where the region ENDS, so the old route was one `source --range` per site over a window whose end you estimate — measured on anyparse for `nodejs` over `src/anyparse/query`: 87 regions, 88 commands, 57 497 bytes, and 25 of the 87 guessed windows never reached their own `#end`. `cond` is one command (40 750 bytes; 27 807 with `--names`). Four things to know. (1) **A branch is not a node** — a whole `#if/#elseif/#else/#end` region projects as ONE node covering every branch, so no selector addresses a branch; `cond` delimits one from its DIRECTIVES (end of its own to the start of the next at the same nesting depth), which makes it nest-safe and parse-free. (2) **Matching is by CONDITION, not by directive text**: `#if (sys || nodejs)` answers `cond nodejs` where `lit '#if nodejs'` sees nothing — in that scope, 87 sites vs 12. (3) **An expression-position `#if`** (`return #if nodejs a; #else b; #end`) projects a CHILDLESS `CondSplice*` node; such a branch is tagged `[raw span]` and printed VERBATIM, and `--names` keeps its bytes rather than reporting an empty symbol list. A file that does not parse is walked too, tagged `[no parse]`. (4) `--limit` counts REGIONS, so **`--max-body N` (default 20) is the flag that bounds output** when the define is a file's top-level guard — uncapped, that same query prints 215 434 bytes. Per-branch tags under "the define is set": `[live]` / `[dead]` / `[maybe]` (another flag decides), plus `[raw span]` / `[no parse]` / `[nested]`. `--active` keeps every non-`[dead]` branch, `--inactive` exactly the `[dead]` ones.
- **A token the parser folds into TRIVIA is invisible to BOTH lint and `fmt --list` — "0 findings + canonical" is not proof it isn't there.** A stray `;` after a block-terminated statement (`for (…) { … };`) gets absorbed into that statement's own span: no node, so every node-based rule reports nothing, and the writer re-emits it verbatim, so the file counts as writer-canonical. It was also load-bearing — its presence SUPPRESSED brace collapsing, so the same construct kept `{ }` around a single statement. Two consequences: (1) when a construct looks wrong but the linter is silent, dump the AST WITH SPANS (`ast --spans` / `probe --spans`) and compare a node's span end against its last child's — the gap is where absorbed tokens hide; (2) detecting them is span arithmetic, not tree walking. Beware the mirror trap: most `};` ARE mandatory (typedef, object literal, `= if/switch/try (…) {…};`, lambda), so gate a detector on a discriminator you verified on a real tree, not on the shape alone.
- **Raw-text search across many `.hx` has no batch reader** — `hxq source` is one file per call and `strip` takes neither a directory nor a glob (`EISDIR` / `ENOENT`). The gate-legal sweep is a loop of `hxq source "$F" --all > out/$F.txt` and then grepping the `.txt` copies (`--all` is required: without it a file over 120 lines writes an EMPTY `.txt` and exits 2, and the grep then finds nothing) (no `.hx` path in the grep command). Expect ~1 process per file; background it for a large tree.
- **Several queries in ONE walk — a bare `--`.** `hxq refs A B C -- src --decls` (also `mentions`, `lit`, `declares`) parses the tree once and prints a `=== <query> ===` section per query, each with its own `--limit` budget and 0-hit nudge; `refs --json` takes ONE name. Without `--` the grammar is unchanged (first positional = query, rest = scope), so every existing call is byte-identical. Measured: 3 names separately = 5108 B / 3 rounds, batched = 1191 B / 1 round — the saving is ROUNDS, not CPU (a name costs ~0.22 s either way).
- **`patch` anatomy — the three failure modes in one line each.** (1) The payload is ONE argument: `old` / `new` fragments alternating, separated by `====` on its OWN line (even section count; N pairs = one call) — multiple payload arguments are rejected. (2) Exactly one of `--select`/`--match`/`--at` is required, and the old-fragment must occur — uniquely — INSIDE the resolved node: `--at` resolves the NARROWEST node (often a bare `IdentExpr`, too small to contain any pair) and `--match` must itself parse as a pattern node (a typedef header or modifier-bearing decl fragment doesn't) → for statement-level edits default to `--select` on the enclosing member/class and widen the old-fragment with surrounding lines until unique, or pass `--all` when the repeat IS the point (the same arm added to every switch that lists a sister enum ctor, one call per file instead of one per site). (3) Copy old-fragments from `hxq source --select` output VERBATIM — it is writer-reformatted (colon spacing, collapsed one-line `if`), so bytes you remember from writing the code may not be the bytes in the node. **Leading indentation is NOT part of the match** — a fragment at column 0, at five spaces, or at the file's exact two tabs all match the same node (verified on a canonical file), so a fragment copied straight out of the dedented `--select` output needs no re-indenting, and the replacement is re-based onto the matched line's own indentation: its first line lands where the matched line was, the rest shift with it by the same amount, and its own relative shape survives. **Until 2026-08-22 that last half was FALSE for anything the writer re-emits verbatim** — the splice began at the matched line's first NON-whitespace byte, so the source's indentation stayed standing and the replacement's own was added on top. In code that is invisible (the writer re-indents it); in a doc-comment interior or a multi-line string literal it was a silent corruption, with `fmt --list` clean, no lint rule reading a continuation prefix, and a string literal's VALUE quietly changed. The op now also refuses a splice into a STRING or REGEX literal whose per-line indentation came back changed line by line (since `e8ec6cc1` comments are exempt — the writer OWNS a comment line's leading whitespace, so a space-gutter doc spliced into a tab-indented site now applies; 343/343 gutter variants) (`the replacement reached the result with its indentation changed line by line`) — the one gate that class of damage has. That makes `the old fragment does not occur` a statement about the TEXT, essentially always the writer's canonical spelling: `a:Int` where you wrote `a: Int`, a one-line `if` where you wrote a braced one. Re-read the node with `source --select` and copy from there rather than counting tabs.
- **A multi-pair `patch` refused as a doc TRANSFER («the edit moves the `/**` block above `<Type>` onto `<member>`») while each pair applied alone was a defect of the guard's position arithmetic — fixed 2026-09-09 (S194, `Patch.shiftedEnd` (named `shiftedDocEnd` until S206)).** The watched doc block's end was shifted by the delta of EVERY edit in the payload, including the ones lying AFTER it, so the refusal fired inside a WINDOW of first-pair growths (measured on base: pads 12–40 and 45–49 of 1…90 refused, 56/34; after: 90/90) and named a member nobody touched. Splitting the call into single pairs is NO LONGER the remedy — a refusal now names a doc that really would move. S206 (2026-09-10) then localised the growth test to the bytes the `/**` block documents: renaming a documented member in one pair and inserting an unrelated declaration ELSEWHERE in the same container in another pair now APPLIES (the doc stays on the renamed member); a fragment that renames the documented member and merely CARRIES the next sibling along applies too. What still refuses, by design and now with a true message, is ONE fragment that both renames the documented declaration and adds a second one (`function b() {}` → `function bee() {}\n\n\tfunction extra() {}`) — byte-for-byte the shape of a real theft. A payload whose first pair REWRITES the doc block and whose second pushes a declaration under it is refused too (it used to apply at rc 0). Known hole (T986): a fragment that STARTS inside a doc block and runs on into code is watched by nothing.
- **Widening an interface with many implementors is impossible under per-op auto-rebuild** — every mutation op rebuilds first and ABORTS on the transient state where implementors lack the new method. Ship a separate capability interface instead (`X implements NewCapability`) so every intermediate compile is green. Same trap in miniature: a multi-step patch that USES a constant before the patch that DECLARES it — run the intermediate op with `HXQ_AUTO_REBUILD=0` (stale binary is safe for a patch; the binary doesn't depend on the file being edited), then rebuild once at the end. Never HXQ_QUIET (kills the staleness check entirely → later probes lie).
- **MOVING a member within its type has no dedicated op — it is `remove-member` + a re-insert, and the whole chain needs `HXQ_AUTO_REBUILD=0`.** Reach for this when `lint --rule member-order --fix` DECLINES ("the reorder is a whole-container permutation and this one would move more than 200 lines for a single reported member, over the review budget") — the finding is real, the autofix is simply over its budget, so the residue is hand-work. Three things make it go wrong otherwise: (1) `hxq source --select 'FnMember:<name>'` returns the member WITHOUT its leading doc, because a doc is trivia OUTSIDE the node span, so capture doc+member by LINE RANGE first or the re-insert silently drops the doc; (2) `add-member` has no position at all — it appends to the end of the type, which is right for "move to the bottom" and wrong for anything else, where `add-element --before|--after --select 'FnMember:<sibling>' --from-file <block> --write` is the op; (3) between the remove and the re-insert the tree does not compile, so the next op's auto-rebuild ABORTS and every remaining op in the chain aborts with it, leaving the type mutilated. Watch the reporting too: `haxe build.hxml 2>&1 | head -N && echo OK` prints OK even on a failed build, because a pipeline's status is the LAST command's — check `${PIPESTATUS[0]}` or drop the pipe.
- **`rename` refuses a new name that an EARLIER op in the same chain already introduced — order, not `HXQ_AUTO_REBUILD`, is the fix.** Distinct from the trap above: `patch` a call site to the NEW name first, then run `hxq rename` on the declaration, and rename refuses — `apq rename: rename to "<new>" is unsafe: the occurrence at L:C is also captured by the rename - qualify the member access or pick another name` — because the name it is asked to introduce already occurs (its own capture-guard re-resolves the tree and checks the occurrence set). `HXQ_AUTO_REBUILD=0` does not help here — the refusal is rename's own safety check, not the build. Fix: run the `rename` FIRST, then the patches that use the new name.
- **`rename --scope` refuses with a FALSE type ambiguity when the cursor file and the scope are written in DIFFERENT path forms.** `hxq rename src/pkg/F.hx … --scope /abs/root/src` reports `type "X" is declared in 2 files under scope — ambiguous, refusing` for a type declared exactly once: the uniqueness check counts the cursor file's relative spelling and the scope walk's absolute one as two files. The message names the wrong problem entirely — you go looking for a duplicate declaration that does not exist (`hxq declares X <scope>` returns ONE row, which reads as the tool being broken). One-variable matrix: relative+relative works, absolute+absolute works, mixed refuses. Rule: spell the cursor path and every `--scope` the SAME way — and treat "declared in N files" on a `declares`-confirmed-unique type as a path-form symptom, not a scope one.
- **`test-summary -` TRUNCATES a large piped stream** — `node bin/test.js | hxq test-summary -` read only ~1583 of 5023 tests and still printed `0 failures` (a partial slice looks green; same hxnodejs stdin pipe limitation as the `Sys.stdin().readAll()` gotcha). For a full-suite run ALWAYS redirect to a file first: `node bin/test.js > out.txt 2>&1; hxq test-summary out.txt`. Piping is safe only for short filtered runs (`APQ_TEST=X node bin/test.js | hxq test-summary -`).
- **A new lint/fix rule green on its unit suite + scratch probes is NOT done yet — run it over a large real tree and READ every site it would change.** A shipped autofix rule, fully green on tests and probes, turned out to make 2 of 10 real matched sites read WORSE than the input (an interior comment preserved but stranded, breaking the construct's shape) — no unit test or scratch probe surfaces that; it's a precondition gap only real code's variety exposes. The real-tree finding list IS the design review — a fixer that makes any real site worse needs a narrower precondition, not a docs caveat.
- **`move` (type to another file/package), the contract measured by S64/S65 (2026-09-03):** the destination file must **exist** (a bare `package p;` module is enough — `hxq new` makes one; ENOENT otherwise). The declaration is a **span splice**, but what lands on disk is canonical-in / canonical-out: a destination that was already writer-canonical is re-emitted through the writer under **its own** `hxformat.json`, a drifted one keeps the spliced bytes. `--scope` is the **resolution index as well as the rewrite set** — a dependency whose module lies outside it binds nothing the op can name and is silently not carried, so widen `--scope` to cover the dependency roots (a `--scope test` move dropped `import anyparse.check.Check;`). A `#if`-guarded import IS carried, re-emitted under its own condition and merged into a same-condition region the destination already has; where one condition cannot carry it (two regions binding one name, deeper nesting, an `#else`/`#elseif` branch, a statement sharing its line with a directive) the move **refuses by name**. A rewrite that fails to re-parse names the file, line and column. Still best-effort: a dependency reached only through a VALUE position (`Type.createInstance(Dep, [])`), a constructor pattern or a lowercase receiver. A module whose parts reference a module-private sibling type cannot be moved by `move` at all (it moves one TYPE; move such modules whole with `patch --select PackageDecl` + `git mv`). It is single-type per call; a 767-module sweep is a loop with a draft commit per batch.
- **Removing a temporary `Sys.stderr` probe: use `remove-element --match`, not a verbatim `patch` revert.** The formatter reflows a long call across lines the moment it lands, so the bytes you inserted are not the bytes in the file and `patch` rejects the old-fragment. `hxq remove-element <f> --match 'Sys.stderr().writeString($x)' --write` deletes one statement per call and echoes the selector it hit; repeat until `grep -c 'Sys.stderr'` is 0 — and always confirm with that count, since a probe surviving a removal pass silently poisons every later measurement. Beware the sibling trap: a probe written as the single-statement body of an `if` leaves an empty `if` behind if you remove only the inner statement — patch the whole `if` + statement as one fragment instead.
- **Wrapping an EXISTING member in `#if … #end`: `patch` the ENCLOSING type, not the member.** A conditional-compilation guard lives OUTSIDE the member's node span, so `patch --select 'FnMember:f'` can never emit it (`the old fragment does not occur`), and no dedicated op adds one. What works is `hxq patch <f> --select 'ClassDecl:<Type>' --write` with the member's whole canonical text as the old-fragment and `#if <cond>` + that text + `#end` as the new one — the fragment search runs over the type's source INCLUDING the trivia between members, so a payload may span comments, blank lines and several members at once, and the writer re-emits the resulting `Conditional` canonically. Copy the old-fragment verbatim out of `hxq source <f> --select 'FnMember:f'` (writer-canonical spelling, flush-left; leading indentation is not matched). **Then re-lint the file**: a lone `#if` block sandwiched between two unguarded members trips `member-order` on the member that FOLLOWS it, with a message about constants/fields/constructor/methods that names nothing about conditionals — the fix is to merge the new guard into an adjacent existing `#if` region (move the unguarded neighbour above it) rather than to reorder anything. Verified 2026-08-17 wrapping a test method in `#if (sys || nodejs)`.
- **A scratch fixture that `lint --fix` SKIPS reads exactly like a refusal.** A hand-written `.hx` probe is almost never canonical, and `--fix` then prints `file is not in canonical form … format it first` above the `0 edit(s)` line — easy to scroll past, and the conclusion "the fixer refuses this shape" is wrong. Run `hxq fmt <dir> --write` on every scratch fixture BEFORE the first `--fix` probe.
  **This is NOT a scratch-fixture problem — it governs REAL trees, and there it is far quieter.** Over a whole project the per-file `not in canonical form` line scrolls away and the only surviving trace is `N file(s) skipped` inside the summary, which reads as bookkeeping. Every hand-edited file in a dirty working tree is therefore INVISIBLE to the fixer — `--fix` is canonical-in / canonical-out: it refuses non-canonical input and its own writes go through the writer round-trip. Measured: 8 files a user had hand-edited survived NINE consecutive full-tree `--fix` passes untouched; one `hxq fmt src --write` made the very next pass find a fix in one of them. So `fmt --write` ALWAYS precedes `--fix`, and the pair must LOOP — they unblock each other, because a fix can be declined while a line is over-width and fire once formatting has split it. Corollary for reading results: a clean `--fix` run over a dirty tree is not evidence the tree is a fixed point until you have confirmed 0 files were skipped. And since `--fix` is canonical-out, drift AFTER a final `--fix` is a tool defect to report, not something to fix with another `fmt --write`.
- **A scratch-file probe of a LAYOUT-sensitive fix (line wrap/indent/braces) is config-blind — same root cause as the `/tmp`-canonical false-refuse and `--fix` no-op notes (references/ops.md, references/lint.md).** `fmt`/`lint --fix` discover `hxformat.json` by walking up from the file being probed, so a bare scratch file gets compiled DEFAULTS, not the target project's style — a probe can show a 1-line result where the project's own config canonicalises the same input to 2 lines. Copy the target's `hxformat.json` next to the probe file, or probe a file inside the project tree instead.
- **`set-doc` takes PLAIN newline-separated text — it derives and adds the per-line doc-comment prefix itself, from the target's indent.** Pass raw lines (`$'line1\nline2\nline3'`); the op wraps them as `/** */` and indents each `* line` to match the declaration (`\t * ` for a member doc, ` * ` for a type doc at column 0). A gutter you write yourself is now STRIPPED rather than doubled (since the S23 fix): only the two spellings the writer emits (` * `, `<tabs> * `) are treated as a gutter, so a markdown bullet (`* item`, `  * item`) and a code sample's indented star keep both their indentation and their star.
- **`comment-rewrite` re-prefixes a MULTI-LINE replacement with the comment's own continuation** (since the S23 fix — literal and `--regex` arms, first line included; `//` continues with `//`, a gutter-less block with its indent, a blank line becomes the bare gutter), **and since S162 it REFLOWS what the edit BROKE**. The trigger is the width gate's own question: unless the edit leaves the comment with MORE over-width lines than it had, or a wider one, nothing moves — so a typo fix inside an inherited 600-column doc line is still just a typo fix (measured: a 7-character edit in `MemberOrder.hx`, whose doc holds a 6641-column line, leaves the file byte-identical to the same edit under `--allow-wide`). When it does fire, every line the edit made too wide is broken at spaces into `wrapping.maxLineLength` with the block's own prefix and indent, at the narrowest width costing no extra line. Nothing is ever JOINED, so your own `$'…'` breaks survive, and a line the edit left BYTE-IDENTICAL is never re-wrapped. **What that fixes is editing a phrase spread over two lines**: a literal find crossing a line break takes the break WITH the text around it, so the two lines merge, and before the reflow the width gate refused every merge past the width (measured on `WriterRefFieldLowering.hx`: 169 columns against 140; the same edit now comes back as 86 and 93). **Four shapes are never re-laid-out, and the op REFUSES rather than wreck them**: a `noqa`/`CHECKSTYLE` directive (breaking `// noqa: some-rule` after the colon widens it to EVERY rule — `Suppression.parseNoqa` reads an empty list as all, and lint then reports FEWER findings, which reads as progress), a `//` trailing after code (its continuation would be a new own-line comment the writer relocates), a line indented past the gutter (a code sample), and a markdown table row or bullet. So is a replacement with NO SPACE inside the width. Each is named in the refusal; `--allow-wide` skips reflow and refusal both, leaving the block exactly as written. **A match starting MID-LINE needs no arithmetic from you** — the reflow absorbs the offset — but it only bounds the line at the CONFIGURED width: a mid-line match can still land a line wider than the block's own wrap style while staying inside the limit (measured 123 columns in `HxFormatSameLineSection.hx`, whose lines are ~80, under a 140 config — legal, and no gate's business). **And a LITERAL find may not cross a blank comment line**: a bare `//` in a run or a bare gutter in a block folds into the same single space an ordinary break does, so such a find used to delete the paragraph separator silently (measured on `HxCasePattern.hx`: the bare `//` gone, two lines merged into 125 columns, inside the width). It is refused now — narrow the find to one paragraph, or use `--regex`, which matches the raw body and needs `\s+//` twice over to cross a run's blank line. An EMPTY replacement is a deletion and still takes whatever break run precedes its match, paragraph separator included.
- **A `$'…'` doc payload containing an APOSTROPHE must escape it as `\'` — the `'"'"'` idiom silently kills the `\n` escapes after it.** `set-doc` / `comment-rewrite` text is prose, so apostrophes are everywhere ("the layer's job", "this op's concern"), and the shell-quoting reflex for a literal `'` inside single quotes is `'"'"'`. That closes the `$'…'` context and reopens a PLAIN `'…'`, where `\n` is two characters — so the first half of the payload wraps correctly and everything after the first apostrophe lands in the file as literal `\n\t * `. The op reports success, `fmt --list` stays clean (comment interiors are re-emitted verbatim), and lint reports nothing: the only tell is reading the block back. Inside `$'…'` write `\'`, never `'"'"'`. When the payload is a whole doc block, prefer `set-doc` (it derives the per-line prefix itself) over patching one sentence with `comment-rewrite`.
- **Driving an op over a real tree to MEASURE it: classify by the op's OWN message, never by exit code.** Every gate on the path answers the same non-zero exit, so a refusal from a DIFFERENT gate reads as a miss of the one you are measuring — and the count looks like a real defect rate. Two artifacts manufacture that reading, both by feeding the op something the earlier gates reject: a probe file copied OUTSIDE the project (no `hxformat.json` beside it → the writer uses compiled defaults → the canonical gate absorbs the case), and probe text invalid for the HOST kind (`function f():Void {}` does not parse in an anon body, so a typedef host dies at the parse gate). Copy the project's `hxformat.json` next to the probe, pick the member text per host kind (`TypedefDecl` → `var n:Int;`, `EnumDecl` → `n;`, else a method), and histogram the stderr text — a clean census is one message, 100% of the rows.
- **`clusters` output columns do NOT discriminate static from instance members.** The `file:line:col` in a `clusters` listing is the NAME token's position, which varies with the modifier TEXT, not the modifier SET — reading "col 17 = static, col 10 = instance" off the listing mis-classified several members. The authoritative member inventory is `hxq ast <f> --select 'ClassDecl:<T>' --depth 2 --children-limit 5000`: modifiers project as separate sibling nodes BEFORE the member, so `(Private)(Static)(FnMember …)` is private static, `(Private)(Static)(Inline)(FnMember …)` private static inline, `(Private)(FnMember …)` an instance method. Parsing gotcha for that dump: when the member node has children the NAME sits on the line AFTER `(FnMember`, not on the same line.
