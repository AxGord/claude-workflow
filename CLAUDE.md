# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

A Claude Code plugin that provides structured workflow orchestration for AI agents via finite-state machines. Bundles an MCP server + SessionStart/SessionEnd hooks. Agents call MCP tools (`start`, `transition`, etc.) to follow state-driven processes. The engine tracks state, enforces guards (max_transitions, max_visits), and manages nested sub-workflow stacks.

Transport: stdio. Packaged as a Claude Code plugin (`.claude-plugin/`).

## Plugin Structure

| Path | Purpose |
|---|---|
| `.claude-plugin/plugin.json` | Plugin manifest |
| `.mcp.json` | MCP server registration (server name: `wf`) |
| `hooks/hooks.json` | Hook declarations (SessionStart, SessionEnd, PreToolUse(Bash), PreToolUse(Write), PreToolUse(Bash|Write|Edit|MultiEdit|NotebookEdit) for the trust-write gate) |
| `hooks/pool-gate.sh` | PreToolUse(Bash): no `pool-gate.yaml` from the payload cwd up to the git root (a command starting with `cd` goes to node, which resolves its target) → exit at once, no node; else `build/pool-gate-hook.js` (`pool-gate.ts`); no node / no build / any error → the command passes as is with one stderr line |
| `hooks/read-only-gate.sh` | PreToolUse(Bash|Write): a payload without `"agent_type":"` → exit at once, no node; else `build/read-only-gate-hook.js` (`read-only-gate.ts`): a read-only agent type's call that would write is denied, its other Bash call runs with the project's read-only env; no node / no build / any error → the call passes as is |
| `agents/*.md` | The shipped subagent types: `workflow:driver` = `templates/drivers/task-driver.md` rules + frontmatter (keep the two in step); `workflow:dispatcher` = frontmatter + a pointer to `templates/drivers/dispatch-driver.md`, its tool list pinned by `dispatcher-driver.test.ts`; `workflow:recon` / `workflow:reviewer` = the read-only types |
| `hooks/trust-write-gate.sh` | PreToolUse(Bash|Write|Edit|MultiEdit|NotebookEdit): with `WORKFLOW_DIR` unset, a payload naming neither `trusted-workflows` nor `workflows` → exit at once, no node; else `build/trust-write-gate-hook.js` (`trust-write-gate.ts`): an agent's write to `$STATE_DIR/trusted-workflows.json` or into the global workflows directory is answered `ask`; only decides, never rewrites (`updatedInput` of one hook breaks the others); no node / no build / any error → the call passes as is |
| `hooks/workflow-start.sh` | Detects plan resume, context clear, or fresh start; first provisions the bundled skills (`build/skills-cli.js sync --quiet`, `src/skills.ts`; copy-if-missing without a build/node; skills dir `CLAUDE_SKILLS_DIR`, else `~/.claude/skills`) and prints a one-time note about edited copies (kept, never overwritten) last, from an EXIT trap; on every start rewrites `$STATE_DIR/context-epoch-<pid>` so the server re-delivers `digest_on_repeat` prompts and `$STATE_DIR/claude-session-<pid>` (the conversation id the server stamps on sessions), deletes the markers of dead pids; on `source: "resume"` picks up the conversation's suspended (or crash-orphaned) sessions for this process, on `compact`/`clear` prints its active ones (`session-cli.js pickup` / `active`; `resume` without a build/node lists the suspended roots) |
| `hooks/workflow-cleanup.sh` | Suspends this instance's active sessions and their active descendants on session end (`suspended_at`, stamped with the ending conversation id; no ledger line — nothing ended), caps retained terminal sessions |
| `scripts/` | Shell scripts exec states run via the engine-injected `$WF_PLUGIN_ROOT`: the `wf-run`, `wf-queue`, `wf-skills`, `wf-trust` shims → `build/*.js`; `skills-history.mjs` (`npm run skills:history`); `check-skill-sync.sh` (bundled-vs-live skill drift check; `.skillsyncignore` lists intentional divergence; in a linked worktree on an `eng/*` branch a bundled skill AHEAD of live — live equals master's bundled — is accepted, and the land runs `sync-live-skills.sh <before> <merged>`, which copies each merge-changed bundled skill to live unless live was edited since or the skill is in `.skillsyncignore`) |
| `templates/` | Bundled workflows (`*.yaml`), `drivers/` (`task-driver.md`, `dispatch-driver.md`), `skills/` (the default skills the start hook copies), `skills-stack/` (language, domain and tool skills: only `wf-skills add <name>` installs one), `skills-history.txt` (the digest of every skill version ever shipped). **Every edit of `templates/skills/` or `templates/skills-stack/` needs `npm run skills:history`** (builds first); `src/skills.test.ts` fails while a shipped version is missing |
| `scripts/export-replay.mjs` | `npm run docs:replay` (after `npm run build`): cuts the landing's replay (`docs/public/replay/anyparse.json`) from the recorded event log, the ledger, the queue file and the pool log through `buildReplay` (`src/replay.ts`); only sessions of `--project` / `--also` are read in, and `assertReplayClean` refuses a write holding a foreign label, an absolute path or a pid |
| `dashboard/scene-dom.js` | The ONE keyed SVG reconciler (`reconcile(parent, groups, els)`: a group per band and lane, an element per `scene()` primitive, changes animating by CSS transition); no state of its own. Used by `dashboard/map.js` (served as `/scene-dom.js`) and by the site's `MapReplay.vue`, so the replay draws exactly what the dashboard draws |
| `docs/` | The documentation site (VitePress, `docs/.vitepress/config.mts`): the pages hold the reference, README the pitch, install and links; pinned by `src/docs-site.test.ts` |

**Tool naming**: `mcp__plugin_workflow_wf__<tool>` (e.g., `mcp__plugin_workflow_wf__start`).

**Dev-machine setup after clone**: wire the drift check as a local git hook —
`printf '#!/bin/sh\nsh "$(git rev-parse --show-toplevel)/scripts/check-skill-sync.sh"\n' > .git/hooks/pre-commit && chmod +x .git/hooks/pre-commit` —
so a commit cannot ship a bundled skill snapshot that silently lags its live `~/.claude/skills/` copy.

## Build & Run

```bash
npm run build    # tsc → compiles src/ to build/
npm run dev      # tsc --watch
npm start        # node build/index.js
npm test         # vitest run (src/*.test.ts)
npm run check    # check:static (tsc --noEmit && format:check (biome) && lint (eslint vs eslint-baseline.json: only NEW findings fail) && scan) && check:tests (vitest && test:pane && check:ci)
npm run check:leased  # npm run check under pool leases sized to each half (2 threads for check:static, then 4-6 for check:tests): scripts/check-leased.sh, what a worker and the gates run, never a bare `npm run check`
npm run check:ci      # the suite in a CI-like environment (scripts/check-ci.sh: `env -i`, fresh HOME, no global git config, foreign time zone and language); part of check:tests
npm run skills:history  # build, then append the digest of every changed bundled skill to templates/skills-history.txt
npm run scan     # ast-grep scan --error: rules/*.yml (sgconfig.yml) are errors, 0 findings; a vetted site takes `// ast-grep-ignore: <rule-id> -- <why>` (needs ast-grep on PATH)
```

Lint = typescript-eslint (`eslint.config.js`, type-checked via `tsconfig.eslint.json`) with a baseline: `npm run lint` fails only on findings absent from `eslint-baseline.json`; fixing old ones → `npm run lint:baseline`. Formatter (biome) is check-only, no mass reformat.

## Environment Variables

| Variable | Default | Purpose |
|---|---|---|
| `WORKFLOW_DIR` | `~/.claude/workflows/` | Global workflow YAML directory |
| `STATE_DIR` | `~/.claude/workflow-state/` | Session JSON persistence |
| `DASHBOARD_PORT` | `3100` | Web dashboard HTTP port |
| `DASHBOARD_HOST` | `127.0.0.1` | Web dashboard bind address |
| `WF_SUSPENDED_TTL_DAYS` | `7` | A suspended session not resumed for this long is abandoned (with its ledger line) at server start |
| `WF_POOL_DIR` | `$HOME/.claude/workflow-pool` | Machine-wide thread pool (`pool.json`, optional `config.yaml`); NOT under `CLAUDE_CONFIG_DIR` — every config dir shares one budget |
| `WF_TRUST_STRICT` | off | `1`: a project file's exec/fetch states load only after `wf-trust` approved that file's sha256; Claude Code's folder trust and project approvals do not count |
| `WF_DISPATCHER` | unset | Set (not empty/0/false/off/no): `start` of the bundled `batch` answers with the dispatcher agent's DRIVER block; needs `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=4` |
| `CLAUDE_SKILLS_DIR` | `~/.claude/skills` | Where the start hook and `wf-skills` copy the bundled skills |

Project-local workflows load from `./.claude/workflows/` (relative to server CWD). Project-local overrides global on name conflict.

## Architecture

### Source Files (`src/`)

| File | Responsibility |
|---|---|
| `index.ts` | Entry point — wires components (its Loader from `workflow-dirs.ts`), starts stdio transport |
| `workflow-dirs.ts` | The one owner of the workflow directories (`WORKFLOW_DIR`, the cwd's `.claude/workflows/`, bundled `templates/`): `resolveDir` / `workflowDirs` / `workflowLoader`, called by `index.ts` and `session-cli.ts` alike |
| `types.ts` | Zod schemas, TypeScript types, constants (`MAX_STACK_DEPTH=10`, `DEFAULT_MAX_TRANSITIONS=50`, `LOCK_STALE_MS=5000`) |
| `engine.ts` | FSM core — `start()`, `transition()`, `abort()`, `setContext()`. Manages snapshot isolation and stack push/pop |
| `loader.ts` | YAML loading + Zod validation (strict: an unknown key fails the load, nearest known key named) + `fs.watch` hot-reload. Three tiers (bundled → global → project, later wins by name), each parsed as `WorkflowFileSchema`; then every name is resolved through its `extends:` chain (`_resolve`) and the MERGED definition is validated; a project-tier file with an exec/fetch state loads only in a trusted project (`TrustStore.allows`), else it is left out and `untrusted()` names it |
| `trust.ts` | Consent for a PROJECT file's exec/fetch states (bundled and global files are not gated): `TrustStore` over `$STATE_DIR/trusted-workflows.json` (`trusted` = per-file sha256, `projects` = directories `wf-trust` approved); `allows(root, hash)` = that hash is approved, or (not strict) the project is approved or trusted in Claude Code; `WF_TRUST_STRICT` counts the hash only, so an edited file asks again; `projectKey` = the directory recorded (a linked worktree → its main checkout) |
| `claude-trust.ts` | Claude Code's own folder-trust answer, read and never written: `ClaudeFolderTrust.trusted(dir)` = `projects[key].hasTrustDialogAccepted === true` in `<CLAUDE_CONFIG_DIR or home>/.claude.json` for a key of `folderTrustKeys(dir)` (the directory and its ancestors up to the git root, never the home directory; a linked worktree → its main checkout only when the pointer is mutual); any read failure = not trusted, and `wf-trust` takes over |
| `trust-run.ts` | `runTrust(argv, store, io)`: the `wf-trust` logic behind a scripted terminal — a project target records the project directory on a typed `yes` (every file in it, edits included), a `file.yaml` target or strict mode records sha256 per file; `--list`, `--revoke <project dir \| hash prefix>`; exit 0 done or nothing to approve, 2 usage, 3 no terminal or not approved |
| `trust-cli.ts` | `wf-trust` (`bin`, shim `scripts/wf-trust`): wires `runTrust` to a real terminal (stdin and stdout must be TTYs; an agent's Bash has none) and `TrustStore.inStateDir(stateDir())`; no MCP tool reads or writes approvals |
| `trust-write-gate.ts` / `trust-write-gate-hook.ts` | `decideTrustWrite`: `ask` for Write/Edit/MultiEdit/NotebookEdit or a Bash command that writes the trust record or the global workflows directory (paths from `stateDir()` / `workflowDirs()`, symlinks resolved; Bash: redirects, `cp`/`install`/`ln`/`rsync` destination, `mv`/`rm`/`tee`/`touch`/`truncate`/`dd of=`/`sed -i` operands, an interpreter's inline code naming the path, `sh -c` bodies, via `splitSegments`); a speed bump, not a sandbox |
| `storage.ts` | JSON session persistence with atomic writes (temp+rename) and `proper-lockfile` mutex (contended locks retry); `update(id, change)` = read-modify-write under that lock for writers outside the transition queue (`setPriority`); `appendLedger` → `ledger.jsonl` (same lock discipline, its own lock file) and rewrites `ledger-recent.jsonl` (the recent lines the plan pane reads, kept under the plugin API's 4 MiB read cap); `readLedger` (every line, a damaged one skipped), `readLedgerTaskRows` (the `taskCostRows` of named queue lines over the WHOLE ledger, indexed once per change of its size or mtime: what `/api/ledger-rows` answers), `readStateJson` (an operator's JSON file of the state directory) |
| `pool.ts` | Machine-wide thread pool (also `projectRoot`, `formatEntry`/`formatStatus` for `wf-run --status` and `pool_status`, `poolSnapshot` for `GET /api/pool`, `reprioritize`): `config.yaml` (`budget`, `load_threshold`, `starve_after`), the pure admission pass `schedule()` (reap dead entries — a lease lives while its pid OR its attached child group does; `external` excludes each threaded lease's own process tree, `treeLoads` over the `ps` table probe; grant in strict priority/arrival order while `held + N <= budget` and, beside a live lease, `held + N + external <= budget` — external never blocks an empty pool — and the waiter's named locks are neither held nor wanted by an earlier waiter, all at once), `Pool.acquire` / lease attach / release under a proper-lockfile lock; load = busy cpus over the cpu-tick window since the pool's previous pass (loadavg1 only without a window); before each pass `_reapOrphans` kills the group of an `owns_group` (`wf-run`) lease whose pid is dead (SIGTERM, SIGKILL after `ORPHAN_KILL_GRACE_MS`; only under the recorded `boot_ms` and leader `pgid_start`, else the lease is dropped unsignalled), `_sampleProcesses` reads `ps` outside the lock with a 30 s backoff, after it `_mark` flags OVERRUN and UNDERUSE (below its threads for `UNDERUSE_GRACE_MS`) leases and STARVED waiters once each into `pool.log` and advances each lease's meter; a release appends its record to `usage.jsonl`; `starvationNotice` is what a starved exec reports (`ExecContext.onStarved` → session `pool_starved` → `starvationLines` in `status`/`transition` of its ancestors); cpu/tick/load/liveness/process-table probes injectable |
| `pool-usage.ts` | What each lease held against what its process tree ran: `LeaseMeter` (`advanceMeter`: a step every 10 s, a gap over 30 s credited to nobody), `usage.jsonl` (`appendUsage` / `readUsage`, rotated past 1 MiB), `summarizeUsage` / `formatUsage` for `wf-run --usage [--since 90m|24h|2d]` |
| `project-settings.ts` | `<project root>/.claude/workflows/settings.json` (a worktree → its main checkout via `projectRoot`; the workflow loader reads only `*.yaml`, so the file is invisible to it): `{ "priority": "low"\|"normal"\|"high"\|"urgent" }`, `projectDefaultPriority(cwd)` — undefined when the file or key is absent, THROWS on bad JSON, an unknown key or a level outside the four (a silently ignored typo would run every task at the wrong level) |
| `wf-run.ts` | CLI over `pool.ts` (`package.json` `bin`): `--status`, `--usage` (per label, held vs used); lease (`--threads N|budget|MIN-MAX`, `--wait-full`, `--lock`; priority from `--priority`, else `WF_PRIORITY`/`WF_PRIORITY_LEVEL`, else the project's `settings.json` level, else 0 — read only on the paths that queue a command; `--status` and `--usage` read neither the file nor the env), run the child in its own group with `WF_THREADS`/`WF_PRIORITY`, forward signals, exit with its code; 75 = busy; `--fail-open` (the pool gate's): a pool that cannot be used → run unleased with the min share + one stderr line |
| `pool-gate.ts` | The pool gate's pure decision (`decide`): `pool-gate.yaml` search (cwd → git root) and validation, quote-aware split into simple commands, rule hits → pass / deny / wrap the whole command under one `wf-run` with the largest share and the `pass` edits (`$WF_THREADS` flag or `env NAME=`); rule `env` conditions on the segment's leading assignments; a `wf-run`/wrapper segment is skipped before any rule, `deny` included; skips `WF_THREADS` set, `wf-run`/wrappers inside, background `&`, heredocs, `WF_POOL_BYPASS=1`. body through `rtkRewriter` (`rtk rewrite`: 0 → allow, 3 → rewrite, 2 → leave alone). `pool-gate-hook.ts` = the hook's stdin/stdout entry |
| `read-only-gate.ts` / `read-only-gate-hook.ts` | `decideReadOnly`: a call by a read-only agent type (`workflow:recon`, `workflow:reviewer`; `agents` in the config overrides) is denied unless every segment starts with a declared reader (`DEFAULT_READERS` + config `read`; no `$( )`/backticks, brace expansion, `printf -v`, `$` in a command word, variable/glob redirect target) and none writes (git write subcommands, file writers, `sed -i`, redirects outside scratch dirs, `sh -c` bodies, the project's `.claude/read-only-commands.yaml` `write` list); otherwise it gets `export <env>;` in front (the rewrite carries `permissionDecision: allow`; beside a segment `unharmlessSegment` names, a call that needs it is denied: run it in its own call). A Write by such a type is allowed only in the task's report directory. A guard against accidental writes, not an adversary. The hook entry also applies the pool gate (`pool-gate-run.ts`) to the env-prefixed command and `pool-gate-hook` skips that agent type: one rewrite only |
| `process.ts` | `killProcessGroup`, `isPidAlive` — shared by executor, engine and `wf-run` |
| `progress.ts` | `withProgress` / `currentProgress` (the progress sink of ONE tool call, an `AsyncLocalStorage`, so concurrent calls never share it) and `startHeartbeat` (a waiting tool call reports every `PROGRESS_INTERVAL_MS`) |
| `template.ts` | `render`: `{{a.b}}` substitution in prompts and action fields (missing → empty, an object → JSON) |
| `yaml-config.ts` | `parseYaml` and `warnLeftoverJson`: the one parser of the engine's hand-edited YAML configs (pool `config.yaml`, `pool-gate.yaml`, `read-only-commands.yaml`) and the one-line warning for a JSON twin left behind |
| `ledger.ts` | The ledger line of an ended session (with the task's `difficulty` / `model` / `effort` / `escalations` / `review_*` / `tokens*` from its context, `spend`, and on a task line `parent_spend`: the top-level conversation's own turns since its previous line, tiled so a turn is in one line); `parseLedger` (a ledger file's lines, a damaged one skipped); `taskCostRows` (the task lines by queue line id, cut to the fields a task's cost needs) |

### Key Design Patterns

**Stack-based sub-workflows**: States with `sub_workflow` property push a new `StackFrame`. Terminal states auto-pop back to parent via `on_complete`/`on_fail`. Max depth: 10.

**Snapshot isolation**: Workflow definitions are snapshotted into an in-memory `Map` at session start. Hot-reloads of YAML files don't affect already-running sessions.

**Overlay modifications**: `modify` stores changes in `session.overrides` (persisted JSON), never modifies source YAML. Overlays are applied at state resolution time in `_resolveState()`.

**Atomic writes**: Storage uses temp file + `fs.renameSync` + `proper-lockfile` for safe concurrent access.

**Session cwd and ids**: `start(cwd)` sets `context.cwd`; execs without their own `cwd:` run there. `start` also fixes `context.project_root` (the main checkout of the cwd via `projectRoot`; refused as a start-context key), rendered as `{{project_root}}` and injected as `WF_PROJECT_ROOT`. Execs get `WF_SESSION_ID` / `WF_PARENT_SESSION_ID` / `WF_ROOT_SESSION_ID` / `WF_PRIORITY` / `WF_PRIORITY_LEVEL` / `AGENT_CONTEXT` (the context tokens of the last turn of the session's linked agent), prompts `{{session_id}}` / `{{parent_session_id}}`. A root ending on a `fail` terminal is `outcome: "failed"`.

**Visit guards**: every move into a state (agent transition, action route, skill-gate auto-transition) goes through `Engine._enterTarget`: past the target's `max_visits` it follows `on_exhausted` (chained, cycle = error) or throws. Pop moves (`on_complete`/`on_fail`) do not check `max_visits`.

**Action results in later states**: `_buildTemplateVars` exposes the session's `last_action_result` (`{{stdout}}`, `{{exit_code}}`, …) to every prompt and action until the next action replaces it — not only to the action's own `success_prompt`.

**Reading a child's results**: `status` cuts each context value to 200 chars; `status({ session_id, key })` returns one value whole (`formatContextValue`), finished sessions included, with no ownership check (like `status`).

**Heavy work through the pool**: an exec with `resource: { threads?, locks?, priority?, wait_timeout? }` (threads, locks, or both) leases from `pool.ts` (the same code path as `wf-run`, not a CLI call) before it runs (`threads: budget` = the configured budget, read when the request is made — a later raise does not grow a waiting or held lease): no lease within `wait_timeout` → exit 75, routed like any exit; abort withdraws the wait; `wait_ms` sits beside `duration_ms` in history and ledger. Light execs never queue. The leased command gets `WF_THREADS` = the threads granted (clamped; absent without threads — `_buildEnv` drops an inherited one). Named locks are machine-wide mutexes granted with the threads in `schedule()`, all or nothing. Threads: the first waiter blocked only by threads is the head; a later one is backfilled ahead of it only if its `est_ms` (p90 from `ledger.jsonl` via `estimate.ts`, read outside the pool lock; `wf-run --est`; else `historyEstimate`: the p90 of the last runs of its `labelKey` in `pool.json` `history`, >=3 samples, recorded by `Lease.release` unless `{ failed }` — `schedule()` also stamps it on an unestimated lease) ends before `headAt` (no "spare threads" rule: a head blocked by threads has none, so every head is a hard reservation); a backfilled lease past 2× its estimate sets `backfill_off` for that head.

**Priority levels and flexible leases**: `PRIORITY_LEVELS` (`types.ts`: low −100, normal 0, high 100, urgent 200) — `session.priority` is set by `start(priority)`, else inherited from the parent, else the project default (`project-settings.ts`, read at `start`; an explicit `priority` and a parent beat it), else `normal`; a lease's priority = level + the step's `resource.priority` (`levelPriority`), recorded with its `level` in the pool entry, and execs get `WF_PRIORITY`/`WF_PRIORITY_LEVEL`. `Engine.setPriority` (tool `set_priority`) writes the level on the session and its active descendants OUTSIDE the session queue, each through `Storage.update` (an ended session stays ended) (an exec of it may be waiting for the very lease) — so `_executeActionState` keeps the level it re-reads after the exec — then `Pool.reprioritize` shifts the waiting entries that carry a level; leases are never touched. `threads: { min, max }` + `wait_full` → pool entry `min_threads` + `full_until` (arrival + window; a waiter with locks stores `full_ms` instead, and `schedule()` stamps `full_until = now + full_ms` on the first pass its locks are free — not held, not claimed ahead — then drops `full_ms`): `schedule()` grants the max when it fits, else after `full_until` the room that fits if ≥ min; a waiting flexible head closes the threads like any waiter; the lease records `threads` = granted (`asked_threads` = the request). A flexible request with an estimate for every size min..max (`est_curve`: `Estimates.curve`/`curveOf` in `estimate.ts` — ledger p90 per size, else `a + b/k` fitted through >=2 sizes; `ExecContext.estimateCurve`; `wf-run --est-by-threads`) skips `wait_full`: `pickByEta` takes the size with the earliest `start(k) + est(k)` (`start` = now if it fits, else `headAt(k)`; unknown start -> not a candidate) and grants it now or waits as the head with `at` = that size's start; behind a head it backfills only a size ending before `head.at`; the lease carries that size's `est_ms`. History/ledger of a leased exec: `threads_granted`, `step_key` = `projectRoot(session cwd)|workflow|state` (`projectRoot`: nearest `.git`, linked worktree → main repo).

**Inheritance (`extends:`)**: `_loadAll` parses each tier into a map of raw files, then resolves every name: a file with `extends: X` = X's resolved definition + its own states laid over by name (whole-state replacement), `initial`/`max_transitions`/`description` from the heir when set. `extends` of its own name resolves from the tiers BELOW the file's tier (project `coding` → global/bundled `coding`), another name from the top tier; `name@tier` links detect a cycle. A file whose resolution or validation fails falls back to the same name one tier down (like a file failing the schema). `_validate` and `validateReferences` see only merged definitions; `extends` never reaches the engine. The bundled `testing` / `bug-fix` expose contract states for heirs (`project_test`, `project_build`, `project_gate` — docs/workflow-yaml.md § "`extends:`"), `batch-task` exposes `project_prepare` / `project_land`; `batch` picks its child workflow from `context.task_workflow`.

**Fan-out and timeouts**: an exec with `fanout: { count | items_command, threads_each, max_parallel? }` (`Executor._execFanout`) runs one instance per shard through `_execLeased` (its own pool lease of `threads_each`, `WF_SHARD=i/N` 1-based or `WF_ITEM`), at most `max_parallel` workers pulling the next shard (default `max(1, floor(budget / min(threads_each, budget)))`, so the pool queue holds only what can run); exit 0 only if all shards are 0, else their common code or 1; `killSession` aborts the fanout (no new shards) besides the usual group kills and lease withdrawals; `ActionResult.shards` → history entry → ledger `execs[].shards`. A foreground exec killed by its `timeout` (a deadline its session's pool waiters, other than the engine's own, stretch through `DeadlineClock`, up to `POOL_WAIT_CEILING_FACTOR`× the timeout; the stretch is the result's `wait_ms`) exits 124 (`EXIT_CODE_TIMEOUT`); `on_timeout` routes it in `_executeActionState` before `cases`/`on_error`.

**Suspend and resume**: a session whose Claude Code process is gone is `suspended_at` (SessionEnd hook, or `reapOrphanedSessions` at server start for a crash), never abandoned: stack, context and children stay, no ledger line. `Engine.resume` re-owns the session and its active sub-tree (`context.claude_code_pid` = this process), clears only the session's own suspension (each child waits for its agent's `resume`), re-snapshots the workflows, and — when the session stopped in an action state — runs `_executeActionState` with its `running_exec`. Every foreground exec runs through `EXEC_WRAPPER` (`executor.ts`): `sh -c` detached, output to `<runDir>/<sid>-<rand>.out|.err`, exit code to `.rc` on exit; `ExecContext.onDetached` records `running_exec` (pgid, files, start, boot time) in the session before the result is returned, the routed write clears it, and the engine removes the files after it. A timed-out run resolves only once its group is dead (`_reapGroup`: SIGKILL after `SIGKILL_GRACE_MS`) — the wrapper dies of SIGTERM even when the command ignores it. The run dir is created 0700; `reapOrphanedSessions` also calls `Executor.sweepRuns` (run files older than a day that no `running_exec` names). A result that cannot be routed (no target, max transitions, max_visits) removes the run's files and the record. `_killSessionProcesses` signals a recorded pgid only under the same boot and while no `.rc` is written (a finished run's pgid can be reused). `Executor.adopt`: `.rc` present → that result; group alive under the same boot → poll until `.rc` / group death / the state's timeout counted from the start and stretched by the session's pool wait (`DeadlineClock`, seeded from the run's `<rc>.wait`; kill → 124); neither → null and the step runs again. An action chain that finds its session suspended or re-owned after the exec throws without routing and leaves the files to the resumer. `transition` / `context_set` / `modify` refuse a suspended session (`assertNotSuspended`). The resume hook's `pickUpConversation` (`takeover.ts`, scope `tree`) re-owns a conversation's suspended or dead-owner sessions with their sub-trees and clears every suspension, without a server; a `running_exec` left behind is then taken by the first `status` (outside the queue only `hasOrphanedExec`, the adopt inside it) or `transition` of the session (`adoptOrphanedExec` → `_executeActionState` with the run; the transition is not taken). `_inFlight` marks the sessions whose action chain THIS engine runs, from the outermost `_executeActionState` to its routed write, so its own `running_exec` is never adopted. `_runActionState` writes `pending_action` (frame, state) before the exec waits for a lease or spawns and clears it with the routed write, an unroutable result, or a throw while the session is still this server's; `_orphanedExec` adopts `running_exec` OR `pending_action` (`orphanedStep`: `exec` = take the run / its result over, `rerun` = run again), and `ExecContext.mayStart` makes a surviving old server give a late lease back unstarted. `_actionNote` replaces `[sub_workflow: unknown]` for an action state in `status`; `takeover.ts` `stepNote` / `drivenByRootAgent` name the step and the sessions with no `agent_id` up to the root in the hook and `resume` lists. The startup reaper suspends only while the session still belongs to the dead pid it read (`_suspendOne`'s `deadOwner`), so a hook handover in between survives. Suspended past `suspendedTtlDays` → `abort(id, "expire")` at server start.

**Difficulty → model/effort**: a workflow's `model_table:` (schema in `types.ts`, merged like `initial` by `extends:`, checked by `modelTableErrors` in `_validate`) is applied by `Engine._withModel` to every write that enters a state (`transition`, skill gate, action route, pop) or sets context (`setContext` and `transition`'s `set`, both through `Engine._withKey`; an exec's `context_set`): the nearest frame down the stack with a table, its visits; a change adds a `model` history line, and `setContext` returns it (the `context_set` answer). `_withKey` refuses a `difficulty` outside 1..10 under a table (for `transition`'s `set` the whole call: no key, no move). `scripts/review-class.sh <base> <tip>` prints the diff's class (`light` tests/docs only, else `code`) for an exec's `context_set: { review_class }`; bundled `batch-task` declares a table, `review_scope` / `review` states.

**Stall detection**: `Engine.staleness(session, parents, now)` resolves the session's state like `status` (an unloadable workflow = a prompt state) and asks `stale.ts`; `Engine.staleLines(id, descendantsOnly)` = one `STALE:` line per stale session of the active sub-tree. `sessions` marks `[STALE: …]`; `status` and `transition` add `staleNotice` unless their answer already shows every line (`unshownStale`) (the lines below the session + one what-to-do line), like `starvationLines`. `{{stale_sessions}}` is a lazy non-enumerable getter on the template vars (only a template naming it walks the sub-tree); `withResult` carries it into the action-result renders (`success_prompt`/`error_prompt`, `context_set`); bundled `batch` `collect` renders it. The loader refuses `stale_after` on a terminal or `sub_workflow` state.

**Task hints**: States can declare a `task:` string. The engine emits `create`/`complete` TaskOp signals in responses, letting the agent manage external task lists.

### Workflow YAML Structure

Workflows are defined in YAML with this structure:
```yaml
name: workflow-name
initial: first_state
max_transitions: 50        # per stack frame
states:
  first_state:
    prompt: "Instructions for the agent"
    transitions:
      next: second_state
  second_state:
    sub_workflow: other-workflow    # pushes stack
    on_complete: done_state        # required with sub_workflow
    on_fail: error_state
  done_state:
    terminal: true
    outcome: complete              # or "fail"
```

Template workflows live in `templates/` for reference. Active workflows go in `~/.claude/workflows/` or `.claude/workflows/`.

### Data Flow

1. Agent calls `start(name, session_id)` → Engine snapshots all workflows, creates session JSON, returns initial state prompt
2. Agent calls `transition(session_id, transition_name)` → Engine validates, updates state, handles sub-workflow push/pop, returns new prompt
3. Session state persisted to `STATE_DIR/*.json` after every mutation
4. Dashboard reads session/workflow data via REST API for visualization

## TypeScript Conventions

- ESM (`"type": "module"` in package.json), all imports use `.js` extension
- Target ES2022, module resolution Node16
- Strict mode enabled
- Immutable interfaces (`readonly` properties) for session state and history
- Zod for runtime validation of both YAML definitions and MCP tool inputs
